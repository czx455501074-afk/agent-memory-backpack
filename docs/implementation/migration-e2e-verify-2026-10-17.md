# 迁移闭环端到端验证（2026-10-17）

功能维度走查的一部分。**全程在隔离沙箱内**（独立 HOME 与数据目录），真实环境未被触碰。

## 一、走通的路径

| 步骤 | 命令 | 结果 |
|---|---|---|
| 1 | `amb init`（源库） | 配置与三组凭据创建 |
| 2 | `amb seed --input good.json` | `imported: 2`，`2 条已写入并生效。` |
| 3 | `amb status`（源库） | 知识版本 1，**知识条目 2** |
| 4 | `amb backup --file library.ambpack --yes` | `dryRun: false`，`bytes: 1413` |
| 5 | `amb init`（目标库） | 配置创建 |
| 6 | `amb restore --file library.ambpack --yes` | `imported: 2`，`wrote: true`，`conflicts: []` |
| 7 | `amb status`（目标库） | 知识版本 1，**知识条目 2** —— **与源库一致** |

**结论：导出与导入确实能跨库携带知识，且计数与版本号一致。**

## 二、幂等性（意外收获）

对同一个包**再导入一次**：

```
imported: 0, skipped: 7, conflicts: [], wrote: false, entries: 10
note: 导入完成，采用合并策略：只新增，不删除。
```

**第二次导入没有产生任何重复写入**（`imported: 0`、`wrote: false`），全部作为"已存在"被跳过。也就是说迁移是**幂等**的，并且**策略是合并而非覆盖**（`只新增，不删除`）。**这两条对于"跨设备搬运知识"这个场景是必要的**——用户不会因为多导一次就得到重复条目，也不会因为导入而丢掉本地已有的东西。

## 三、过程中的两个副产品

### 1. 撞到并修好了一个真实的报错缺陷

按"以用户身份走一遍"执行到第 2 步时，输入文件的字段与 schema 不符，而命令只回了一句 `Configuration or import schema is invalid`——**不说字段、不说文件、不说怎么改**。已修：现在输出形如

```
输入不符合格式要求：
  entries.0 —— 含有本命令不认识的字段（unrecognized_keys）
```

并且修的时候保留了原有的防泄露顾虑（该校验库的错误消息可能引用提交内容），只透出**结构性的字段路径与错误码**（描述位置与类别、不引用任何值）。这一处不是读代码发现的，是走这一步时撞出来的。

### 2. 这次的输入字段是照着错误提示补全的

修好提示后，我依据它把输入从"多写了字段"改成**只写必需字段**（`id`/`kind`/`title`/`scope`/`body`，其余字段都有默认值），一次通过。**这本身就是那条修复有用与否的验证**。

## 四、未覆盖

- **没有测**大库迁移（本次只有 2 条）；没有测包损坏、版本不符、部分表缺失等情况下的行为。
- **没有测**跨机器/跨平台的迁移（本次是同一台机器上的两个目录）。
- **`backup` 与 `restore` 的输出目前仍是原始 JSON**（与 CLI 其余部分已统一为"默认给人看、`--json` 给脚本"的约定不一致），**列为待办**。
