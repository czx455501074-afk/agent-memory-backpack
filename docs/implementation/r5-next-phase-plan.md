## 三、下一阶段候选（按"用户能感知的价值 / 成本"排序）

**P1 — 召回预算与渐进披露（W12 正在做）**：这是用户最初诉求里"不要把大量上下文喂给 agent"的另一半。真实分布：中位 1460、p90 4429、最大 8312 字符/轮。完成判据：给出超预算时的省略规则、省略内容如何取回、以及同一条查询前后字符数对比。

**P2 — 提炼器从骨架变成可用产出（W11 第二阶段）**：它决定"经验能不能持续进来而不淹没审核面"。已有普查依据：140 条失败事实、47 个签名、≥2 次阈值可丢掉 37 组/37 条。完成判据：跑一轮 dry-run，给出会产出几条候选、每条出自哪个签名、以及人工审阅一批后的质量反馈；在拿到反馈前，参数保持保守且标注为未校准。

**P3 — 归属死结的结构性处置**：库里 workflow 与 task 条目均为 0，导致每条经验提交都"未归属"。P1/P2 依赖候选能正常流转，所以这条要在 P2 落地前生效。完成判据：一条内容合格的候选在不合成任何 workflow 的前提下能被列入队列并采纳。

**P4 — 面板目视确认与宿主级触发**：三项目视项（折叠区、被拦候选、预填）与两项宿主级触发（`task.archived` 日志、指针级注入样本）。完成判据：重启宿主后，日志里出现 `task.archived`，且 `context.injected` 出现 ≤200 字符的样本——**这是"核心就绪"变成"用户拿到"的唯一证据**。

**P5 — 排序质量调参**：长度因子来自单一样本，`strong` 项不参与归一。完成判据：用一个分布级语料（而非个例）给出调参前后的命中率对比。

## 四、明确不做（以及原因）

- **不改失败事实的去重键**：去掉 sessionId 会让"同一错误出现次数"无法增长，直接毁掉聚合视图与提炼阈值的前提。
- **不合成 workflow 来解归属问题**：那是为了让检查通过而制造数据，会让"归属"这个字段失去意义。
- **不自动采纳任何提炼结果**：审核门禁是这套产品的核心承诺，自动采纳与它冲突。
- **不做跨平台**：当前验证只在 Windows x64 完成，没有第二个平台的实测证据，声称支持会是猜测。

## 五、衡量这一版是否真的有用（不是"功能是否存在"）

发布后看四个数，它们都能从现有日志与库里算出来：

1. `context.injected` 的**中位数**是否下降（当前 1460）；
2. 指针级样本数是否从 **0** 变成常态；
3. `pending` 的**日增**是否低于人工处理速率（当前一天 204 条产出 vs 四天 11 个决定）；
4. `in_progress` 任务里"有结束事件却仍未收敛"的条数是否保持在 0（当前已由收敛规则清零）。

前两个衡量"省了多少上下文"，后两个衡量"待办是否可控"。**如果发布后这四个数没有变化，那么这一版的改进就只存在于测试里。**
