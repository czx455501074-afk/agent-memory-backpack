# 结构性审计（2026-10-17）

按发行目标要求的四个维度之一做结构审计。**先看结构，再看规模**——行数本身不是判据。

## 一、模块规模

`src/` 29 个文件 / 12066 行；`adapters/` 22 文件 / 8086 行；`scripts/` 14 文件 / 3359 行。

最大的几个：`store.ts` 3446 行（占 src 的 29%）、`ui.ts` 1564、`cli.ts` 1112、`server.ts` 700，适配器侧 `client.js` 2321、`index.mjs` 2178。

## 二、依赖结构：健康

用脚本解析全部相对导入，得到 **29 个节点 / 72 条边，循环依赖 0**。

- **扇入最高**：`schema.ts`（被 15 处依赖）——它是底层的类型与校验定义，被广泛依赖是它的职责。
- **扇出最高**：`cli.ts`（12）、`server.ts`（10）——两者都是入口，依赖多是正常的。

**没有环、层次清晰**：底层是 schema/config/log，中间是 store/retrieval，上层是 cli/server/ui。

## 三、最大的文件该不该拆：不该

`store.ts` 有 **70 个公开方法**，覆盖知识读写、检索、门禁、候选审核、任务、外发队列、迁移等多个域。**单看这份清单，像是把好几个模块塞进了一个文件。**

逐个核对后，**它们是同一件事：对同一个数据库的读取与写入**。域虽多，**职责单一**（数据访问层）。而且"集中"有一个反向的好处：**所有数据库操作在一处，审计才做得成**——此前的 SQL 注入检查之所以能通读全部 115 处 `prepare(` 并逐条确认无用户输入进入查询文本，正因为它们都在同一个文件里。

拆分要付出的代价是**共享状态**：拆开后各文件仍需访问同一个数据库句柄与事务上下文，**收益只是行数变小**。行数变小本身不是目标。**判定：不拆。**

## 四、最长的函数该不该拆：不该

用脚本扫描函数体长度，最长的真实函数是 `store.ts` 的 `submit()`（310 行）与 `adopt()`（192 行）。

看 `submit()` 内部：**绝大部分是注释，实际代码约 40 行**。注释记录的是**已经踩过的坑与当时的权衡**，例如：

- 幂等重试必须**先于**新鲜度校验——顺序曾经相反，导致已存在的候选被误判为 `revision_conflict`，调用方拿不到它应得的回执；
- payload 必须在**这一层**也校验——HTTP 边缘已有 schema，但外发队列重放路径直接调用此方法，曾因此把一个空字段存成候选、并让缺字段的请求以裸 `TypeError` 失败；
- 工作流归属**记录而不丢弃**——曾因"未知工作流 id"直接中止提交，**实测造成 21 次失败调用的文本永久丢失**，而那是本项目唯一禁止的结果；
- 精确文本重复检测取代模糊合并——审计项 EV-CE-02：同一文本在不同幂等键下两次入队，都判为新增，采纳后重复入库。

**这些注释是资产，不是噪声。** 拆这个函数会把它们和代码分开，而它们恰恰解释了代码为什么长成现在这样。**判定：不拆。**

## 五、找到并修掉的不一致：错误处理有两套

统计全 `src/` 的错误抛出方式：`throw new DomainError` **141 处**（带错误码、统一处理、面向用户），`throw new Error` **43 处**。

其中 `cli.ts` 占 24 处，**16 处消息为纯英文**，并且**会原样展示给用户**（捕获处输出 `Invalid arguments: <message>`）。也就是说：**项目其余部分都已经中文化，只有这条路径会让用户一打错参数就撞上英文，而且不解释那个参数是干什么的。**

已全部改为中文，**保留参数名**并在有帮助时补上用途，例如：

```
改前  Invalid arguments: --old ID and --new ID are required
改后  缺少 --old 与 --new：需要「被取代」与「取代者」两个条目 ID

改前  Invalid arguments: --dir DIRECTORY is required (the export target, e.g. ...)
改后  缺少 --dir：导出目标目录（例如 <项目>/.agents/skills/amb）
```

改完全量套件仍全绿（dist 443/445、mjs 117/117，均 0 fail）。
