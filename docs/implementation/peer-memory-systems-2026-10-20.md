# AMB 记忆质量与检索覆盖：同类系统研究

研究日期：2026-10-20，Asia/Shanghai。范围：5 个有公开源码和官方文档的代表性项目；不以 star 数量判断质量，不安装、不接入其服务，不修改真实知识库。本报告提供机制比较与实施建议，不声称已验证其他项目在 AMB 数据上的效果。

## 结论

AMB 已经具有 global/project/task、journal/norm/skill/memory/preference/workflow/material、来源与证据等级、候选审核、替代关系以及分块读取。用户感受到的失准不能简单归因为“没有类别字段”。应优先验证这些信息是否在每条写入、审核、自动捕获和读取路径中得到一致执行。

借鉴价值最高的是：Mem0 的受上下文约束的提取、Graphiti 的“当前有效事实与历史事实分离”、claude-mem 的“索引→前后文→批量正文”、Letta 的“核心上下文与按需资料分层”、QMD 的“多路召回与保护精确命中”。这些机制可以逐步加入现有 SQLite/HTTP/MCP 架构，无须先迁移到图数据库。

## 1. Mem0：有上下文的提取，身份边界由调用参数确定

**核实机制。** 当前 `add` 默认通过模型提取，`infer=False` 直接保存原内容；user/agent/run 标识控制归属，expiry 可使条目默认不参与搜索。当前源码将身份键从普通 metadata 剥离，再由显式实体参数写入过滤条件，避免元数据覆盖归属。[官方 Add 文档](https://docs.mem0.ai/core-concepts/memory-operations/add)、[归属与提取实现](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/memory/main.py)。

当前主路径采用 ADD-only 提取；提示词要求只从新消息提取，旧记忆用于去重和链接，区分 user/assistant 归因，略过寒暄、空泛确认和无内容元评论，时间相对词按事件发生日期解析。[当前提取提示词](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/configs/prompts.py)。

**局限与 AMB 建议。** 不宜照搬早期材料中“add 自动 UPDATE/DELETE”的描述：当前源码保留部分旧提示词，并不证明当前 add 主路径使用它。Mem0 的个人助理提取偏向多记；工程插件应增加“是否值得跨会话使用”的独立判定。归属优先取宿主确认的 project/task/session，模型只建议是否扩展范围，不能因为内容写得像通用原则就直接 global。

## 2. Letta：常驻核心与按需正文分开，定期整理而非每次堆积

**核实机制。** 当前 Agent SDK 文档使用 MemFS：`system/` 下的记忆每轮进入系统提示，其余文件通过目录按需读取；记忆受 Git 管理。Dreaming 可按步数或压缩事件触发整理；共享仓库的云端和自托管能力不同。[当前 Memory 文档](https://docs.letta.com/agent-sdk/memory)。

旧 V1 文档则使用 memory blocks、shared blocks、archival memory 的术语；不能把两代接口当作相同 API。[V1 stateful agents](https://docs.letta.com/v1-sdk/concepts/stateful-agents)。

**局限与 AMB 建议。** 常驻内容和 agent 自己修改的内容需要明确权限与审计；周期整理也会产生错归纳。AMB 可保留数据库作为权威，把“短小、已确认、当前有效的规则/事实”与“原始事件/候选/资料”分层检索。整理输出先形成带来源的候选变更集，保留旧版本和撤销路径。

## 3. Graphiti / Zep：事实有效期、证据来源和历史关系

**核实机制。** Graphiti 为事实保留有效窗口、源 episode 和替代历史，支持语义、关键词、图关系的混合检索；官方明确区分开源 Graphiti 与托管 Zep，后者的用户/会话治理与性能承诺不能套到自建版。[官方 README](https://github.com/getzep/graphiti/blob/7b0182f94d27075db488636cd5456981ee10b987/README.md)。

`EntityEdge` 分别保存 `created_at`、`valid_at`、`invalid_at`、`expired_at`、来源 episodes 与 reference time；“事实何时成立”和“系统何时判失效”是不同信息。[边结构源码](https://github.com/getzep/graphiti/blob/7b0182f94d27075db488636cd5456981ee10b987/graphiti_core/edges.py)。

**局限与 AMB 建议。** 自动抽取/冲突判定仍需要可靠模型，完整图数据库和嵌入运行成本超出现有轻量架构。先在 SQLite 中借用 lifecycle 和关系表：当前有效、待复验、已替代；记录 observedAt、复验条件、失效依据与 successor。一次 429、下载失败、工具未开放，应留下事件事实及重试条件，不能派生永久禁行路线。

## 4. claude-mem：渐进检索和时间上下文

**核实机制。** 官方工具工作流为 search 获取简短索引，timeline 找前后文，再批量 get_observations 获取正文；支持 project、日期、类别和分页。当前搜索文档说明：向量可用时先语义匹配，关键词补足空的记录类别，向量不可用时由关键词响应。[官方工具文档](https://github.com/thedotmack/claude-mem/blob/3fae1eb45ba1a7fbd4818527f48b439991a273da/docs/public/usage/search-tools.mdx)。

**局限与 AMB 建议。** 找到局部观察不能保证覆盖全部解决步骤；时间相邻也不一定语义相关。AMB 已有目录和分块读取，可增加“本次是摘要/节选/完整正文”“有哪些相关块和关联条目尚未读”的结构化回执。先以确定的行/块覆盖度推动续读，再加入受预算限制的关联拓展。不要把更多返回内容直接等同于更完整。

## 5. QMD：多路召回，保留原查询和精确命中

**核实机制。** QMD 以本地文档搜索为核心，组合 BM25、向量、query expansion、RRF 和 rerank；对原查询与高排名命中有保护。collection/path context 为结果提供来源语境。README 还明确默认嵌入对 CJK 的覆盖有限，允许换模型并重建嵌入。[官方 README](https://github.com/tobi/qmd/blob/86d2365d17fc682e491c2c53d1e4a884aee8682a/README.md)。

**局限与 AMB 建议。** 它主要解决“找文档”，不替 AMB 决定规范权限或经验有效性；多模型下载和推理是额外成本。AMB 已有可选向量和 RRF，优先完善原词/别名/中英术语/错误码召回，保留原查询；只有明确低召回时才启用有界扩展。中文工程资料需在自己的评测集上选模型，不能借英文指标宣称效果。

## 与 AMB 当前源码的对应关系

以下为本次只读审阅所得，不是完整根因审计：

| 用户问题 | 已存在的机制 | 应继续核对的执行点 |
|---|---|---|
| 全局/项目/会话失准 | `src/schema.ts` 定义 global/project/task；task 有 sessionIds | session 和 task 是多对多关系，不能直接互换；缺失上下文是否仍被默认扩权；导入、候选、自动事件各入口是否一致 |
| 日记/规范/技能混淆 | schema 明确各 kind，semantic/model-review 有分类 | 自由文本分类有启发式和建议层；候选最终采纳路径是否保留来源、证据、scope 和最终类别；混合内容是否拆分 |
| 无意义内容收录 | 提交工具要求先规范化；分类 gate 存在 | 所有写入入口是否都经过质量判定；“不够持久”应保留日志还是拒收长期知识，是否可解释 |
| 临时错误固化经验 | material 有 expiry；有 supersession 历史 | 普通 memory/skill 中的故障经验是否缺少复验期限和适用环境；过时内容是否仍参与默认注入 |
| 只找到一部分就停止 | retrieval-chunk 已有 outline、hasMore、nextChunkIndex；prepare 有 coverage 提示 | 文档未读块、搜索未返回页、问题各子目标覆盖是三件事；字段是否被适配器完整透出；是否有真实任务验收 |

本次还确认 `src/retrieval-service.ts` 已实现可选向量融合、覆盖过薄时降级、RRF，以及选择来源回执；因此“增加向量”本身不是充分修复。自动注入少量候选是预算策略，不能承担穷尽搜索的契约。

## 建议实施优先级与验收

### P0：将归属、类别、有效性拆成独立判定

建议把分类收据稳定为：宿主上下文、建议 scope、建议 kind、durability、证据来源、置信/未知、原因、是否可直接采纳。类名正确不代表证据可靠；项目无关也不代表全球适用。不要使用一个综合分替代这些独立维度。

优先保证：缺失 project/task/session 时不擅自补成 global；明确“本次/此会话”不能扩展为长期规则；agent 自己的命令口吻不能升级为用户规范；同一提交同时包含过程、结果和方法时，可建议拆分，保留原候选供复查。模型不可用或不确定时，窄作用域/待核实应明确标注，不能伪称精准判断。

**可验证案例：** 同一条 429 在两个项目出现，不形成全局禁用 API；“这次用 X”归当前 task；用户明确“所有项目都要 X”可以提出 global norm，但其用户授权来源必须保留；带 AGENTS.md 字样的错误报告不因文件名直接归 norm。所有入口跑同一组夹具。

### P0：临时故障使用生命周期，不产生永久回避

暂态故障先记录“发生了什么、何时、在哪个版本/环境、后续如何检查”，不直接概括为“不要使用此途径”。只有确认稳定根因和适用边界后才成为可复用知识；恢复或新版本的反例应可替代旧结论。

若第一步尚不加入数据库字段，可先在候选分类层将 temporary/unknown 明确落为 task journal 或待审核 memory，禁止自动成为 skill/norm；这属于过渡措施，不等同于完整时效管理。

**可验证案例：** 超时后成功不能仍默认注入失败禁令；旧环境限制默认不影响新环境；历史仍能通过显式历史查询找到；续期必须给出复验证据，不能因“再次被搜到”自动延长。

### P0：让返回结果明确说明“还缺什么”

确定性信息先做：本次返回类型、总匹配数、已返回范围、next offset/cursor、文档总块数、当前块、hasMore、outline、正文版本。把“读到某一块”与“读完相关资料”分开，结果排序和续读必须保持同一版本和同一可见范围。

问题覆盖可另外列 `coveredTopics`、`uncoveredTopics`、`relatedIds`，但必须注明这是检索提示，不是证明所有知识已被搜索完。对用户询问多个子目标的场景，记录每个目标的支持来源和未找到项。无需强制全库通读。

**可验证案例：** 关键修复在第 3 块时，读第 1 块的结果仍提示后续；第二个相关条目提供恢复步骤时可继续找到；零结果能区分真无匹配、过滤后为空和模型/向量降级；跨项目续读不泄漏数据。

### P1：以复用价值为中心的知识整理

为候选准备 skip / event-only / task journal / durable proposal 四种处置。寒暄、重复确认、空结果和工具流水默认不进入长期知识；事件层仍可保留必要诊断信息。合并时保存来源 id、结论修订和冲突关系，避免反复检索十条碎片后重新总结。

不要因“缺少测试输出”就一概丢弃事实，也不要让 agent 在 evidence 字段写了“验证过”便自动变成 observed；证据等级必须取自可核对记录。

### P1：用盲测证明“越用越聪明”

在独立夹具库中建立多项目、多会话、中英术语、暂态故障→恢复、冲突替代、多文档步骤等样例，保留预期相关 id 和必要正文片段。评价至少包含：scope 错扩率、类型混淆、噪声长期入库率、过时建议注入率、Recall@K、完整支持证据覆盖率、额外 token/延迟、降级可解释率。

用“收录前→收录后→出现修正证据后”的同一问题对比结果。仅重复搜索已知条目或断言字段存在，无法证明长期学习。旧数据先做只读质量报告和可审核变更清单，不能直接批量重分类、删除或推广为全局规则。

## 不确定性与实施边界

1. 没有实测以上系统在 AMB 数据上的准确率、吞吐和资源占用；官方宣传性节省比例与延迟没有被当作 AMB 交付指标。
2. 本次仅抽查 AMB schema、分类与检索相关源码，未审阅真实库中的每条候选，也未证明某个入口就是唯一根因。
3. Graphiti 的 temporal 设计、Letta 的当前 Agent SDK 与旧 V1、Mem0 的当前 ADD-only 路径均有版本差异；实施时以锁定版本的主调用路径为准。
4. 上述建议中的字段名是设计示意，不是现有 API 承诺。需先匹配现有契约和备份兼容性，再确定持久化形式。
