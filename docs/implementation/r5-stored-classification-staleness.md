# 存量候选的分类判定是"写入时的快照"（2026-10-17 新发现）

## 现象

W2 把分类器修好之后，离线回放显示：用新判定重跑，待审候选里判为 `norm` 的从 232 条降到 13 条，反向新增 0。测试也全绿。

但直接数真实库里的存储判定：

| `payload.classification.kind` | 条数 |
|---|---|
| **`norm`** | **255** |
| `memory` | 96 |
| `preference` / `material` / `skill` | 5 / 2 / 2 |

**360 条待审里仍有 255 条被标为规范（71%）**，与新判定完全不符。

## 为什么

`payload.classification` 是候选**提交那一刻**写下的判定快照。分类器逻辑更新后，**没有任何机制重算已入库的判定**。于是：

- 回放证明"新判定会判成 13 条"——这是**如果现在重跑会得到什么**；
- 库里存的是"当时判成了 255 条"——这是**今天用户会看到什么**。

两件事都真实，但只有后者决定用户体验。

## 更严重的一半：存量候选会绕过新的采纳门禁

W7 的采纳侧接线是这样写的（`adapters/dsh/index.mjs:706`）：

```js
if (classification.autoPromotable === false) return null
```

`autoPromotable` 是 W2 **新增**的字段，**存量候选没有它**。而 `undefined === false` 为假，所以：

**255 条被标为规范的存量候选，仍然可以一键采纳为参与工具门禁的硬规范。**

也就是说，"经验不再被一键升格为规则"这条修复：

- 对新提交的候选：**有效**（字段存在且为 false 时被拦）；
- 对用户此刻面对的存量队列：**无效**（字段缺失被当成放行）。

W7 自己在报告里点出过这个风险（"可选门禁字段必须用 `=== false` 而非 falsy"），当时是为避免误拦正常候选；但它同时意味着**缺失字段落在放行侧**——而缺失恰恰是存量数据的常态。

## 需要做的（尚未做）

1. **采纳侧改保守**：判定字段缺失时不得一键采纳，而应要求人工选定类别与作用域，并说明"该候选的判定来自旧版本，无法据此自动放行"。理由要人能读懂，不能只是一句"不放行"。
2. **存量回填**：用当前分类器重算待审候选的判定（幂等、可 dry-run、有明确入口），并**在 payload 里记录分类器版本**，使"这个判定出自哪一版判定器"可查。这样下次分类器再变时，能识别出哪些判定已过时，而不是又一次静默地新旧混用。
3. **验收判据**：修后 255 条应降到与实际相符的数量级（真规范约 13 条 + 少量残留），且**没有任何候选能绕过人工确认**；同时用只读回放给出前后数字。

## 为什么之前没发现

W2 的 6 项测试构造的是**新提交**的候选（带新字段）；回放脚本重算的是**内存中的判定**，两者都不经过"库里已存了什么"这条路径。**测试覆盖的是代码，不是数据。** 这条记下来，是因为同类缺口会随每次分类器改进重复出现。

## 另一半：门禁只装在一个适配器里，服务端并不拦

顺着上面那条查下去，发现缺口的形状比"字段缺失"更大：

| 采纳入口 | 有无 `autoPromotable` 门禁 |
|---|---|
| DSH 适配器（面板按钮） | 有，但用 `=== false` 判断 → **字段缺失时放行** |
| **网页管理界面「批准并生效」**（`src/ui.ts:810` 的 `approveProposalForm`） | **完全没有**——直接构建 entry 并 `POST /v1/proposals/approve` |
| **网页管理界面「批量批准」**（`src/ui.ts:1345`） | **完全没有**——可一次批准勾选的全部候选 |
| 服务端 `/v1/proposals/approve` | 只要求请求方自带 `entry`；**不检查分类判定** |

也就是说：**"经验不会被一键升格成规则"这道门禁，装在一个客户端里，而且对它最需要拦的那批数据（没有该字段的存量候选，255 条标着 `norm`）是放行的。** 换一个入口（网页界面）就完全不经过它，批量入口还能一次过 N 条。

真正的问题不是"某个字段没判断"，而是**审核门禁的位置**：它必须在服务端强制，而不是依赖每个客户端自愿遵守。客户端可以做的是"提前告知与预填"，不能是"唯一的关卡"。

## 修法（尚未实施）

1. **服务端强制**：`/v1/proposals/approve` 在分类判定为"不得自动升格"（`autoPromotable === false`）**或该字段缺失**时，要求请求方显式声明"已人工确认类别与作用域"；缺失不是放行理由，而是"必须由人确认"的理由。响应里要说清为什么需要这次确认。
2. **客户端一致**：网页界面的单条与批量入口都走同一条服务端判定，不再各自为政；批量入口在存在"需确认"的候选时，要么逐个确认、要么明确告知这批里有几条需要人工确认后再提交。
3. **存量回填**：用当前分类器重算待审候选的判定，并在 payload 里记录分类器版本，使"这条判定出自哪一版"可查——否则下次改进又是一轮静默的新旧混用。
4. **验收判据**：修后 255 条应降到与实际相符的数量级；并且从**任意入口**（适配器、网页单条、网页批量）都无法在没有人工确认的情况下把一条判定为"不得自动升格"的候选写进库。三条入口各留一条测试。
