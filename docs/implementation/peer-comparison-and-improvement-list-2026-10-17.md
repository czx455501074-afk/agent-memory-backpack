# 同类项目对比与改进清单（2026-10-17）

本文件回应发行目标里的"逐板块对比同类项目并形成改进清单"。**对比只写有出处的部分**：一类是实际读到的同类项目说明（DSH 生态的插件），一类是早前读过的多系统横向对比材料。**没有出处的猜测不写进来**。

## 一、对比对象与出处

| 对象 | 出处 | 性质 |
|---|---|---|
| `dsh-memory-evolve` | 其 README（本地材料库，本轮与上一轮均读到） | DSH 生态内的记忆插件，功能面最宽 |
| `dsh-mnemon` | 其 README 与架构说明（本地材料库） | DSH 生态内的记忆插件，架构分层清晰 |
| 12 个记忆/MCP 系统 | 早前读过的横向对比文档 | 覆盖 MCP Memory、Basic Memory 等 |

## 二、逐板块对比

**① 安装与首启**

- 同类：一行宿主命令（`dsh plugin --profile <p> add <pkg>`）+ 重启，**bundle 自动注册**；并明确警告**不要手工 insert**，否则加载器报重复 id。
- 我们：**机制相同但此前只写在脚本里**。本周期已核实并写进 README：那条一行命令一直可用，实测在独立临时 profile 上退出码 0、bundle 自动增加、补丁层保持为空。
- **结论：已补齐**（差距是文档而非功能）。

**② 版本化与可追溯**

- 同类：记忆条目普遍是"当前值"；`dsh-mnemon` 提供候选保存回执与备份，但**未见完整修订沿革**。
- 我们：**每一条都有修订沿革**（`revision` 单调递增，可查历史），候选与采纳记录分离，另有任务日记。
- **结论：我们更强，保持**。这是本项目的核心差异点，不该为了"对齐同类"而弱化。

**③ 审核与门禁**

- 同类：多为"AI 直接写入"，少数提供确认回执。
- 我们：**候选必须经审核才生效**（pending → 采纳/拒绝/归档），且注入前有门禁校验。
- **结论：我们更强，保持**。

**④ 记忆的产生方式**

- 同类：**回合内自动提炼**（每隔 N 轮由模型主动提炼并交用户确认）、**技能自我进化**（反复踩坑自动固化成技能）。
- 我们：**靠显式提交**（`amb_submit_experience`）与显式结构化。
- **结论：我们弱于同类**。这是**真实的体验差距**——自动提炼把"要不要记"的负担从人转移到了系统。
- **处置：列为待做项（见第三节 T1），但不在 1.0 范围**：自动提炼会直接改变写入链路与审核负载，属于需要单独设计周期的功能。

**⑤ 检索**

- 同类：多层策略，含语义检索；`dsh-mnemon` 有 Sources/Strategies 分层。
- 我们：词法（含中文 bigram 索引）+ 可选的模型选择，**无向量检索**。
- **结论：广度上弱于同类**，但本周期实测发现**默认路径（模型选择）在这批查询上召回更少、更慢，且会漏掉明显该命中的条目**（查询「托盘」返回 0 条），而词法路径稳定命中。
- **处置：列为待做项（T2）**，且**在查清前建议默认走词法**。

**⑥ 界面呈现**

- 同类：有专门的"记忆条""Memory System"页面，`dsh-memory-evolve` 另有无限画板、会话评审等一整套 UI。
- 我们：DSH 内嵌面板（五个视角：全部/按类别/待审/任务/管理）+ Tauri 桌面控制台。
- **结论：功能面窄于同类，但覆盖了本项目最需要的三个动作**（看、审、迁移）。
- **本周期已做**：候选行内容显示、展开全文、按钮层级、**键盘焦点可见**（此前完全没有焦点样式，键盘用户无法使用）。
- **处置：保持当前范围**，不做画板这类外围能力。

**⑦ 迁移与备份**

- 同类：`dsh-mnemon` 提供 ZIP 备份；MCP Memory 类系统多数无迁移机制。
- 我们：`.ambpack` 打包 + 导入预览 + 跨设备携带。
- **结论：我们更强**；已知边界（历史修订含密钥形状内容会挡住导出）已单列并标注。

## 四、这份清单的自限

- **对比对象只有两个 DSH 插件读到了原文**，其余来自早前一份横向材料；**同类项目的内部实现没有读**，因此"同类如何如何"只说到其文档所声称的程度。
- **"更强/更弱"是对功能面的判断，不是质量评测**：没有跑基准、没有对比资源占用、没有做用户研究。
- **T3/T4/T5 的"不做"是取舍而非结论**：如果本项目定位变化（例如要做会议话归档），这几条都该重新评估。

## 五、联网复查补充（2026-10-17 稍晚）

第一至四节基于早前读到的两个 DSH 插件与一份横向材料。本轮按要求重新联网检索，**发现了此前未接触过的同类**，其中 [agent-memory-mcp](https://github.com/ipiton/agent-memory-mcp)（Go）与 [memory-bridge/忆桥](https://github.com/yanglinfeng/memory-bridge) 与本项目定位最接近，值得单独对照。

### 5.1 与本项目思路重合的部分（说明方向没走偏）

`agent-memory-mcp` 独立走到了许多相同结论：**分层知识**（raw memory 与 canonical knowledge 分开，接近本项目的 pending → active）、**取代链**（`superseded_by` / `replaces` 双向链接，接近本项目的 `revision` 沿革）、**审核收件箱**（接近本项目的候选队列）、**可解释检索**（debug 输出分数构成，接近本项目的 `selection.mode` + `reason`）、**漂移检测**（对比记忆与仓库文件，接近本项目的 `rescan`）、**本地优先 + SQLite**（与本项目相同）、**HTTP 默认只绑回环**（与本项目相同的安全默认）。

**两个独立实现收敛到同一批做法，是好信号**；这说明"可追溯、可审核、不破坏性"这套取向不是偏门。

### 5.2 它做而我们没有的

| 能力 | 说明 | 我们的判断 |
|---|---|---|
| **按时间点检索**（`recall_as_of`） | "在某时刻什么是真的"——用 `valid_from`/`valid_until` 与取代链回答历史问题 | **本项目具备数据基础**（每次修订都留档），**缺的只是一个查询入口**。列为 T9（见下） |
| **自动会话捕获** | 用宿主 hooks 在会话结束时自动提炼并入库 | 本项目是显式提交 + 宿主 hook 的**部分**自动（Codex 侧有 hook）。**这是有意取舍**：自动入库会改变审核负载 |
| **多跳检索**（知识图谱三元组） | 抽取 (主体, 关系, 客体) 支持多跳查询 | **不做**：需要额外的模型调用与图谱维护，与"当前规模下词法已够"的判断一致 |
| **神经重排序** | 混合检索后再上一道 cross-encoder 重排 | **不做**：需要外部推理服务；本项目连向量检索都刻意未引入 |
| **语义检索 / 向量索引** | 嵌入模型 + 向量存储 | **不做（有意取舍）**，理由见第三节 T5 |
| **面向工程工作流的专用工具** | `store_decision` / `store_runbook` / `store_incident` 等 | **部分等价**：本项目用 `kind` + 工作流结构化表达同一意图 |

### 5.3 我们做而它没有的

- **双宿主适配**：同一份知识同时服务 DSH 与 Codex 两端，含各自的注入与门禁；对方的客户端配置是逐个生成的，不涉及"两端共用一份规范"。
- **任务交接与检查点**：`checkpoint_task` / 任务日记，把跨会话的进度与未完成项落进同一个库。
- **规范门禁**：`gate` 在注入前按任务与宿主身份校验，回答"这一次用哪条规则"。
- **批准与采纳的分离**：候选、采纳记录、取代记录是三类可分别审计的事实。

### 5.4 `memory-bridge` 的一条启发

它的定位语里有一句值得记：**"每个答案带逐句出处与可回放 traceId"**。本项目的注入回执已经带 `reason` 与来源，但**没有"可回放的 traceId"**——即由一次回答回溯到它当时用了哪几条知识的完整链路。**列为 T10**。

### 5.5 本节新增的改进项

| 编号 | 改进项 | 状态 | 理由 |
|---|---|---|---|
| T9 | 按时间点检索（`recall_as_of` 等价能力） | **待做** | 数据已在（每次修订留档），缺查询入口；对"这条规范什么时候开始生效/失效"这类问题有直接价值 |
| T10 | 注入的可回放 traceId | **待做** | 现在能说"用了哪些知识"，还不能把某次回答与当时的知识快照一一对回；需要先设计存储位置与保留期 |
| T11 | 自动会话捕获（更完整的 hook 化） | **不在 1.0** | 同 T1：会改变审核负载，需独立设计 |
| T12 | 多跳检索 / 神经重排 | **不做** | 需要外部推理依赖，与本项目"可离线、可解释"的取向冲突 |

### 5.5.1 上述各项的最终处置（2026-10-17 稍晚更新）

本节列出的四项已全部处置，不留悬空：

| 编号 | 处置 | 说明 |
|---|---|---|
| **T9 按时间点检索** | **已完成** | 数据基础本就具备（每个修订都带时间戳），实现只是补入口：库方法 `asOf` 与命令 `amb asof --at`，并有单元测试。 |
| **T10 可回放 traceId** | **核心已完成** | 注入回执（`prepare` 返回的 `retrieval`）本就含 `query`/`tokens`/`matchedTokens`/`gaps`/`selected`，**只缺每条的修订号**；补上后与 `asOf` 配合即可重构一次过去的注入。**持久化刻意不做**：回执由调用方持有，把每次注入都存库是保留期决策，不是代码决策。 |
| **T11 自动会话捕获** | 不在 1.0 | 会改变审核负载，需独立设计。 |
| **T12 多跳检索 / 神经重排** | 不做 | 需要外部推理依赖，与"可离线、可解释"的取向冲突。 |

**另有一项不来自本节的对照，而是来自本项目自身的测量**：**T2 显式检索的降级行为**。追查后发现注入路径与显式检索**调同一套选择逻辑，却对"模型什么都没选"处置不同**——注入回落本地排序，显式检索返回空集，**同一查询因入口不同得到两个答案**。已统一为都回落，并把原因改写为 `model_abstained:<原原因>` 保留区别（详见发行判定文档 10.7）。

**并留下一项独立问题**：模型路径的**首条有时不相关**（例如查询「导出守卫」返回《DSH Client Slot…》）。这与降级行为无关，属**选择质量**问题，按"未做的要写清为什么"的原则单列，不计入本次修复。

### 5.6 本节的自限

- 只读了 `agent-memory-mcp` 的 README（长达数万字，**未读其代码**）与 `memory-bridge` 的仓库页标题与简介；**`dsh-advanced-memory` 的 npm 页面被反爬拦截，未读到**，故未纳入对比。
- 对比依据是**对方的文档所声称的能力**，未做实测；本项目的各项能力则均有本周期实测记录。
- 这两个项目比本项目新接触到的同类**功能面更宽**，但**功能多不等于更适合**——本项目刻意收窄了范围（见第三节的分类）。

## 六、第二轮联网复查：分发与生态（2026-10-17 晚）

前两轮比的是**功能**。这一轮换了个问题：**同类项目是怎么被用户拿到的**。结果比功能差距更值得先解决。

### 6.1 发现：DSH 生态已经有一个带规则的插件目录

[awesome-deepseek-harness-plugins](https://github.com/imsai-sh/awesome-deepseek-harness-plugins) 收录 **13802** 个插件（含 PR 收录与 GitHub `dsh-plugin` topic 自动发现），其中**「记忆」类 437 个**。它不只是列表，还有在线市场、装进 dsh 本体的市场插件、免费查询 API。

关键不在数量，在**它的分发规则**：

- **只提供 npm 安装**：详情页给出的命令安装的是"作者发布到 npm、声明 `dsh.bundle`"的包。
- **未发 npm 的插件只能"浏览模式"收录**：有仓库链接，**没有安装命令**。
- 收录前过静态校验：读取默认分支的 Git tree，检查 `package.json`、`dsh.bundle.patch` 字段，以及 patch 文件在同一棵 tree 里确实存在；**全程只读，不装依赖、不执行仓库代码**。

### 6.2 对照：我们站在哪一边

| 维度 | 本项目 | 判断 |
|---|---|---|
| 声明 `dsh.bundle.patch` | ✅ `adapters/dsh/package.json` 有 `dsh.bundle.patch`，patch 文件同树存在 | **已满足**该目录的静态校验条件 |
| 发布到 npm | ❌ 未发布（README 早就承认 `npx` 走不通） | **未满足**安装前提，因此在该目录里只能是"浏览模式" |
| 包自包含可运行 | ✅ **本轮实测**：`npm pack` → 干净项目 `npm i <tarball>` → `amb --version` 输出 1.0.0、`--help` 正常、`doctor --offline` 结构化输出 | 分发形态本身是好的 |
| 一条命令安装 | ❌ 需要 clone + build + install:local，或 `dsh plugin add` 一个本地路径 | 已知的体验差距 |

**结论：差距不在功能，不在包结构，而在"没有发布动作"**。而发布 npm 需要账号凭据与人工审核，不是代码能替的。

### 6.3 本轮据此做的三件事（都不需要发布凭据）

1. **补 `--version`**：市场页、issue 模板、用户反馈都会先问版本，而此前 `amb --version` 的回答是 `Invalid arguments: Unknown option`。
2. **修掉不可执行的建议**：`doctor` 的提示原本写 `node dist/src/cli.js service start`——对装了包的用户，这个路径不存在。现改为 `amb service start`，并把路径写法保留为"源码目录里的等价形式"。
3. **验证 tarball 真的能用**：不只看 `npm pack` 成功，而是**装进一个空项目再跑**。这一步才发现上面那两条（`--version` 缺失、建议不可执行）。

### 6.4 新增改进项

| 编号 | 改进项 | 状态 | 理由 |
|---|---|---|---|
| **T13** | 发布到 npm（`agent-memory-backpack` 与 `dsh-agent-memory-backpack` 两个包） | **待执行，需要凭据** | 这是该生态的**唯一安装前提**。包结构与自包含性已就绪（6.2 实测），缺的是发布动作本身 |
| **T14** | 提交目录收录 | **待 T13 之后** | 有 npm 包后才会被"安装模式"收录；否则只能浏览 |
| **T15** | 首启"一条命令" | **部分达成** | `dsh plugin --profile <p> add "$PWD\adapters\dsh"` 已写进 README 并实测；比同类的 `add <npm 包>` 多一步 clone |

### 6.5 这一节的自限
