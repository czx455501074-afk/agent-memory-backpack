# 落库前必须写规范描述（原文不入库）

**规则一句话**：任何数据写入知识库之前，**由 agent 先写出一段规范、全面的描述**，再把**那段描述**落库。原文（会话流水、工具输出、整段源文件、抓取到的网页正文）不作为知识正文落库。

## 一、为什么（有数字）

原文入库要付两次账，而且两次都不在写入那一刻暴露：

**检索竞争**。长文本天然累积查询词，排序里因此压过真正的短条目。本项目此前已实测过同一现象：一篇 20,735 字符、**引用**某条规则的日记得 4.0000 分，而规则本身（69 字符）只有 2.0866——规则险些被它自己的引用挤掉。

**注入预算**。注入是按字符计费的。真实库普查（`node verification/knowledge-normalization.mjs`，2026-10-18）：

| kind | 条目 | 原文型 | 占比 | 原文型占用字符 |
|---|---|---|---|---|
| material | 246 | 25 | 10.2% | 353,870 |
| memory | 224 | 10 | 4.5% | 310,068 |
| journal | 205 | 2 | 1% | 7,306 |
| skill | 152 | 29 | 19.1% | 375,433 |
| **合计** | **912** | **66** | **7.2%** | **约 104 万字符** |

**7.2% 的条目占掉百万级字符**。最长的几条是 `memory:c982bd91bcda51cb`（53,116 字符）、`memory:bf3a73b52978f737`（50,495）、`memory:cfff3dd316eda3b1`（44,258）——开头都是 `[00:00] [915新剧本] 【生成】EP001 S08c…` 这种**带时间戳的流水**，而不是一条能复用的结论。

## 二、规范的描述必须具备什么

一段合格的落库描述，读的人**不必读原文就能判断该不该用它**：

1. **标题即结论**（不是"某次做了什么"，而是"什么情况下该怎么做/什么不成立"）。
2. **适用条件与不适用范围**：什么情况下这条成立、什么情况下会反过来。
3. **判据**：可复算的检查动作（判据句 + 期望结果），而不是"我当时这么做的"。
4. **证据以指针形式给**：命令、文件、数字、条目 id —— 而不是把整段输出贴进来。
5. **超出预算的部分留指针**：长内容写成"摘要 + 用 `amb_read_knowledge` 读全文"，而不是全文内联。
6. **去掉一次性的东西**：临时 taskId、本机绝对路径、当轮的对话时间线。

## 三、禁止的原文特征（与脚本判据一一对应）

命中**两条及以上**即视为原文型（`verification/knowledge-normalization.mjs` 的 `SIGNALS`）：

| 特征 | 为什么算原文 |
|---|---|
| `transcript-prefix` 以流水时间戳开头 | 这是一条记录，不是一个结论 |
| `tool-output` 正文里贴了整段工具输出 | 证据应当是指针 |
| `first-person-log` 逐轮自述过程 | 过程不是知识 |
| `dense-local-paths` 长正文里密集出现本机绝对路径 | 只对这一台机器成立 |
| `code-dominant` 以代码块为主体 | 等于把源文件搬了进来 |
| `oversize-no-pointer` 超长且没有指向完整内容的指针 | 读者只能全读或全不读 |

**阈值取"两条"是刻意的**：一条可能是误报（合法条目里引用一条命令很正常），两条说明同一段文本被两个不同角度指着。

## 四、示例对照

同一件事，两种落法：

**原文型（现状，不可落库）**

```
[00:00] [915新剧本] 【生成】EP001 S08c／S07 重发核验（libtv）。S08c 重发成功落盘：新 taskId 2…
[19:01] [915新剧本] 在 DSH 环境侧安装 dsh-memory-evolve 插件（web profile）：该插件不在 n…
（下略 5 万字流水）
```

**规范型（应落库）**

> **标题**：libtv 重发镜头时，先核验上一版是否仍在画布上，再提交生成
> **适用**：画布上已有同镜头的旧版本、需要重发时。不适用于首次生成。
> **判据**：① `libtv node list --group <组>` 能查到旧节点 id；② 重发后新节点与旧节点**同时存在**，不是覆盖；③ 核验下载文件大小与画布记录一致。
> **证据**：`taskId 2…`（当日重发记录，已归档）；命令见 `libtv-cli` 技能。
> **完整过程**：见 journal `journal-task-…`（按需读取）。

## 五、落点：在哪些写入路径执行

| 路径 | 现状 | 要求 |
|---|---|---|
| `amb_submit_experience`（agent 提交经验） | 直接写候选 | **提交前先写规范描述**；工具描述里已写明 |
| `amb_checkpoint_task`（任务检查点） | 写摘要/未完成项 | 摘要写结论与判据，不写过程 |
| 自动捕获（`autoCaptureFailures` / `autoCaptureMaterial`） | 默认关闭 | 开启时仍是"观察记录"，**不参与阈值统计**这条已生效；开启后须按规范改写才采纳 |
| `adopt`（采纳外部知识） | 有整理步骤 | 采纳的是整理后的条目，不是源文件 |
| 材料（`material`） | 抓取网页原文（中位 16,000 字符） | 原文可留作可追溯引用，但**不应作为知识正文参与检索**：保留摘要 + 来源 URL + 失效时间 |
| 技能（`skill`） | 导入 `SKILL.md` 正文 | 技能正文是**指令**，属于该场景的合理形态；但 19.1% 命中原文特征，说明其中混进了日志与整段源文件，应拆成叶子文档 |

## 六、怎么执行（不要只写成文档）

```powershell
node verification/knowledge-normalization.mjs            # 普查：分 kind 的原文型占比与最需要改写的条目
node verification/knowledge-normalization.mjs --json      # 机器可读，供看板与回归比对
```

- 脚本**只读、不判定旧数据有罪**、退出码恒为 0。它把"要改写多少"变成可核对的数字。
- **新写入**按本规范执行；**存量 66 条**的处置见下节。
- 门诊断与落点已登记在 `docs/release-checklist.md` 第二节的发布前必过项。

## 七、存量治理（不擅自改用户数据）

66 条原文型条目分三类，处置方式不同：

1. **会话流水型（memory，10 条 / 31 万字符）**：从流水里提炼出结论 → 写成规范条目 → 原流水**归档**（`archive`）而不是删除，保留可追溯性。
2. **抓取原文型（material，25 条 / 35 万字符）**：保留摘要与来源 URL，正文改为"摘要 + 指针"；材料本就有 90 天失效期。
3. **技能正文型（skill，29 条 / 37.5 万字符）**：把日志与整段源文件拆进叶子文档，主文档只留指令与索引。

治理动作**由人或经审核的 agent 执行**，脚本不提供批量改写：改写知识正文等于改写历史，必须留下修订记录。

## 八、边界

- **不是所有原文都该消失**：审计需要原始记录（事件流就是为此存在），材料需要可追溯原文。规则约束的是**它是否作为知识正文参与检索与注入**。
- **这条规则不能靠"拒绝写入"执行**：与导出守卫同样的教训——只会拒绝的门禁，最终会被人用"删点东西直到能过"绕过。所以做法是**先写描述**（本文件）+ **可核对的普查**（脚本）+ **提交时的要求**（工具描述），而不是写入失败。
