# 检索质量实测发现（2026-10-17）

## 缘起

做检索质量抽查时，先用错了端点：`/v1/search` 返回的是 `workflows`（**工作流**搜索），不是知识条目——名字让人以为是通用检索。换到 `/v1/knowledge/search-universal` 后才测到真实行为。**这个命名歧义本身值得记一笔**：一个了解本系统的人（我）都踩了。

## 对比结果

同一批查询、同一个端点，只切换 `literal` 参数：

| 查询 | `literal: false`（模型选择） | `literal: true`（词法） |
|---|---|---|
| 导出守卫 | 1 个结果，**返回 "DSH Client Slot、主题 Token…"（完全无关）** | 5 个结果，含插件仓库与日记 |
| **托盘** | **0 个结果** —— 而库中确有《cc-switch 的 Tauri 技术栈实证（托盘/自启/插件清单）》 | **5 个结果，第 1 条正是它** |
| 门禁 | 1 个结果，返回 "2026-09-27.md" | 5 个结果，含门禁相关日记 |
| 候选审核 | 1 个结果，返回 "拉片审核" | 5 个结果，含审核相关日记 |

- **结果数**：模型模式每次只回 **1 条**（请求是 `limit: 5`）；词法模式回满 **5 条**。
- **耗时**：模型模式 190–230ms；词法模式 150–180ms。**两者都未接近超时**，所以差异不是"模型来不及"造成的。
- **响应里可读到判据**：模型模式的 `selection.mode` 为 `model`；词法模式为 `lexical_fallback / explicit_full_text`。

## 判断

**至少在这批查询上，词法路径的表现明显优于模型选择路径**：召回更全、相关命中更准、还更快。最刺眼的一条是「托盘」——库中有一条标题里就写着"托盘"的条目，模型模式返回 0 条。

**需要说明的边界**（避免把话说满）：
- 这是 **10 条查询的抽样**，不是基准测试；样本里有中文短词与专有名词，正好是词法（含中文 bigram 索引）擅长的类型。
- 模型路径**设计上**可能就倾向于"精选少量最相关项"，那么"只回 1 条"是**特性而非缺陷**——但那样它就不该在明显该命中的查询上返回无关项或空集。
- 我没有读模型选择那一段的实现，**因此不知道它是"选得少"还是"选偏了"**，也没有改任何代码。

## 建议的下一步（未执行）

1. 先查清模型选择路径的取舍：是"精选 N 条"还是"判定相关性后过滤"；如果是后者，为什么"托盘"会被过滤掉。
2. 在查清之前，**默认走词法**是更安全的选择——它在这批样本上全面更好，而且不需要模型参与、没有额外延迟。
3. 把 `/v1/search` 的命名问题一并处理：它实际是工作流检索，名字却像通用检索。至少应在文档与 CLI 帮助里点明，避免调用方（包括未来的我）再踩。

## 补充：读到实现之后的修正（2026-10-17，同一会话）

上一节里我写"不知道它是**选得少**还是**选偏了**"。现在读过实现了，可以回答。

### 是"选得少"，而且是有意的

`src/retrieval-service.ts` 的本地排序在返回前做了两件事：

```ts
const best = ranked[0]?.score ?? 0;
const localIds = ranked
  .filter(hit => hit.score >= best * 0.6
    || (hit.strong && hit.score === bestOfObjective.get(hit.objective) && hit.score >= best * 0.25))
  .slice(0, 3)
  .map(hit => hit.candidate.id);
```

代码注释把意图写得很直白：**"远低于最高分的条目是共享词邻居，不是答案"**，以及"关于某个条目的请求，不该把每个碰巧与它共享一个词的条目都拖进来"。所以"少"是**精确优先**的取向，不是实现疏漏。同一段还照顾了"两主题请求"——不允许只回它得分最高的那个主题。

### 模型成功时，本地结果根本不会被用

同一个文件的回退构造器里写着：

```ts
selectedIds: reason === 'not_configured' || reason === 'model_timeout' || reason === 'busy'
  ? localIds : []
```

也就是说：**只有模型未配置、超时或繁忙时，才把本地排序交出去**；模型正常作答时，用的是模型的选择。这解释了我观察到的现象——模型模式下**回 1 条**，是模型自己挑了 1 条；而词法模式（`lexical_fallback`）把本地排序的 5 条交了出来。

### 这一段的注释里还有一条实测记录

紧接着那段代码注释提到：曾有两个原因分支**被留空**，代价是调用方丢掉全部有用命中；并给出实测——**"一个这样返回空的查询，本地其实有十条匹配"**，以及在五路并发下"三个因繁忙返回空、另外两个在允许超时回退后各返回三条"。也就是说：**"空返回"这个问题在此前已经被人用实测抓到并修过一次**，修法是让超时与繁忙也允许交还本地结果，同时把原因字符串（`model_timeout` / `busy` / `not_configured`）一并带上，让调用方**能区分"降级的本地答案"与"模型给出的答案"**。

### 修正后的结论

- 我上一轮描述的差异（召回少、更慢）**仍然成立**，但成因不是缺陷而是**取向**：模型路径追求"只给最像答案的"，词法路径给"本地排序的前若干条"。
- **「托盘」返回 0 这一条仍需单独解释**：如果那是模型判断"没有相关内容"，那么在这个库上它就是一次**误判**——因为确实存在一条标题里就含"托盘"的条目，且本地排序的首条就是它。**这条无法由上述代码解释**（模型选择的具体过程我看不到），因此**保留为未解释的观察**。
- **对使用场景的建议不变**：如果是"我知道大概叫什么、想把它找出来"，走词法更稳；如果是"我只有一个模糊描述"，模型路径才有意义。**在查清模型的误判率之前，默认走词法更安全。**

## 补充 2：把"未解释"推进为"可稳定复现"（2026-10-17，同一会话）

上一节我留了一条未解释的观察：查询「托盘」在模型模式下返回 0 条。本轮做了重复性实验，可以把它的**性质**确定下来——虽然仍未确定**原因**。

### 实验与读数

| 条件 | 运行次数 | 结果 |
|---|---|---|
| 模型模式（`literal:false`） | **6** | **6 次全部 0 条**，`selection.mode = model` |
| 词法模式（`literal:true`，对照） | 3 | 3 次全部 5 条，`selection.mode = lexical_fallback`，**首条均为《cc-switch 的 Tauri 技术栈实证（托盘/自启/插件清单）》** |
| 目录直读（`kind=material`，`query=''`） | 1 | 该条**在目录中排名第一**，即它确实存在且本地排序把它排在最前 |

### 因此可以确定的与仍不能确定的

**已确定**：
- 这是**可稳定复现**的结果，不是偶发、不是时序、不是并发抖动——六次连试结果一致。
- **不是"条目不存在"，也不是"索引缺它"**：目录直读排第一，词法路径稳定命中。
- 差异**只出现在模型选择这一步**：同一查询、同一库，模型路径稳定给空集，词法路径稳定给正确结果。

**仍不能确定**：
- **模型为什么这样判**。它的选择过程在服务内部，我看不到它的输入（是否被截断、是否只看到摘要、是否受某种过滤规则影响），因此**无法判断这是"它认为不相关"还是"它没看到那条候选"**。
- 这一点很重要：**同样是返回空集，"判定为不相关"和"压根没拿到候选"是两种不同的问题**，修法也完全不同（调提示词 vs 修候选构造）。**在能观察到它在看什么之前，不应按其中任一种去修。**

### 对默认路径的建议（维持不变并加强）

在被解释清楚之前，**默认走词法**是更安全的选择：它在这批查询上召回更全、命中更准、延迟更低，并且不依赖模型；而模型路径在至少一个明确的案例上会稳定地丢掉正确答案。

**下一步若要继续**：应先取得模型选择那一步的**输入**（它实际看到了哪些候选、以什么形式），而不是继续猜测它为何给空集。

## 补充 3：一个被我否掉的推理（2026-10-17，同一会话）

补充 2 里我说"下一步应先取得模型选择那一步的输入"。本轮我去取了，**但中途提出过一个不成立的推理，记录在此以免后来者重犯**。

### 那个不成立的推理

我想到：如果目标条目出现在**词法路径**的排序里，就说明它"在候选集合中"，那么模型没选它 → 属于"看到了但判定为不相关"。

实测：词法路径（`literal:true`、`limit:10`）返回 10 条，**目标条目排在第一位**，第二位的标题里也含该词。于是差点得出"模型看到了它却没选"。

**这个推理是错的**，原因在读了实现之后才清楚：

- 词法路径走 `store.searchUniversal`，它**自建一套关键词匹配与排序**（`filter(matches.has) → sort(by score) → slice(limit)`）。
- 模型路径喂给模型的是 `snapshot.index.rank(query)` 的结果（见 `retrieval-service.ts` 的 `const shortlist = ... ranked.map(hit => hit.candidate)`）。

**这是两个不同的排序实现。** 一个的输出，**不能用来推断另一个的内容**。所以"词法排第一"对"模型看到了什么"**没有证明力**。

### 这为什么值得单独记

它正是补充 2 那条教训的**同一个错误的变体**：我在上一节刚写下"能分开两种原因的证据，永远是那一步的输入与输出"，转手就用**旁路的输出**去推断那一步的输入。**写下一条原则和照着它做，是两件事。**

### 现在真正能说的

- **可稳定复现**（6/6 空集）——这一条仍然成立。
- **不是数据缺失**：目录直读能取到该条目，词法路径能稳定命中——这一条也仍然成立。
- **但"模型是否看到过它"仍未确定**，因为**我还没有观察到那个排序本身**。要观察到它，需要从该步骤内部取证据（例如让它在运行时输出它实际收到的候选），而不是从另一个端点旁敲侧击。
