# R5 真实用量报告（2026-10-17）

这份报告回答一个不能靠测试回答的问题：**这套东西在真实使用里到底占多少上下文、留下多少待办。**

数据来源是插件自己写下的日志与知识库，**只读**读取。生成命令：

```powershell
node scripts/r5-usage-report.mjs          # 人看的版本
node scripts/r5-usage-report.mjs --json   # 给脚本/CI 用的版本
```

## 一、窗口可比性（先说清限制，否则数字会骗人）

- 统计的事件类型统一为 `context.injected`，其余事件不参与比较——按本项目既有规范，跨类型求和的"总数"没有意义。
- 时间窗：**2026-10-16T19:54 → 2026-10-17T11:19**，共 114 条记录。这是一个连续窗口，不是两个可比周期的对照，所以下面**只做分布描述，不做"改进前 vs 改进后"的因果声明**。
- 日志里没有 `selection.mode` 字段，因此**无法从日志判断每轮走的是模型路径还是本地索引路径**。要判路径必须直接问运行中的核心（见 [`r5-acceptance.md`](r5-acceptance.md) 第三节）。这是本报告的一个明确盲区。

**一天产出 204 条待审、且基本没被处理**，这就是"待核目录"在真实使用中的样子：产出速度远超人工审阅速度。叠加聚合视图后，用户面对的是 224 条可审项（84 条重复被折叠成 46 个签名），仍然远超"一天能看完"的量。

**结论：聚合只是让队列可读，不解决产出量。** 真正要动的是产出端——负向过滤（本机路径、一次性命令噪声不提炼）、观测阈值（同签名出现次数下限）、每次产出上限。这正是 W11 第二阶段在做的事，也是这份报告给出的直接依据：**没有这组数字，"要不要限流"就只是一个观点。**

## 五、这份报告不能证明什么

- 不能证明"修复让上下文变少了"——窗口不构成前后对照，而且指针级样本为零，任何"节省比例"的说法都会是编的。
- 不能证明检索质量——日志不含检索走哪条路径、命中了什么。
- 不能证明用户的主观体验——它只是把可计量的部分量出来。
