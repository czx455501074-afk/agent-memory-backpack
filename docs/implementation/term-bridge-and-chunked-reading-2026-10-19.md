# 术语桥与分块读取：让库回答用户真实的问题，也让长条目真的被读完

> 起因是用户报的两个现象：他在另一个项目会话里提到"装插件之前就已经落库的技能、规范"，
> agent 却听不懂；以及一些数据文本过长，agent 没有主动读完。用户追问的核心是**术语桥**：
> 别的项目有没有？我们要不要？如果不用它，怎么保证 agent 准确全面地取到所需内容？
>
> 这份文档记录实测取证、同类对照结论、设计与验证。**数字都是当次实测**，改动结构后请重跑。

## 一、取证：三个缺陷，全部量化

| 缺陷 | 实测 |
|---|---|
| **术语桥 100% 缺失** | 库里 173 条 active 条目，**173 条没有任何桥字段**（无 summary/aliases/keywords；只有 title） |
| **同义说法完全落空** | 用「我以前写下的那些规矩」查，`matched=0`、`shown=0`；而库里那 4 条规范全在，标题写的是「规范」 |
| **长条目只读开头** | 正文平均 **7459** 字符、最长 **53117**；`amb_read_knowledge` 一次给全文，`prepare` 只注入前 **400** 字符 |

补充两条同样重要的观察：

- **`/v1/search` 与 `/v1/knowledge/search-universal` 是两个入口**：前者只搜流程（`workflows`），
  后者才是全库。用错入口会把"没搜到"当成"库里没有"——**先读真实投影再下结论**。
- **规范类查询走的是第三条路**：`prepare` 会把 `hostProvided: true` 的规范**排除注入**（宿主自己
  已经注入过，插件刻意不重复发送正文），这在设计上是对的；但那段回执过去**只列 id**
  （`norm:39399196b561fdbc@1`），既不说明它讲什么、也没说怎么取。

## 二、同类项目对照（子代理调研，区分"实读"与"推断"）

**术语桥这一侧**：六个项目里没有一个用"术语桥"这个叫法，但都有一层等价物。

| 项目 | 做法 | 证据强度 |
|---|---|---|
| Basic Memory | frontmatter 的 `title/type/tags/permalink` + `Observations` + wikilinks；**每个 observation 单独索引**；链接按 permalink → title/path 解析 | 实读官方格式文档 |
| Cognee | chunk / summary / 事实多路候选，**RRF 融合**（`rrf_k` 限在 30..60），可乘 importance（`0.75 + 0.5*importance`） | 实读 `ranking.py` |
| Zep / Graphiti | 节点全文索引建在 **`node_name_and_summary`** 上；BM25 / 向量 / BFS 多路候选，**RRF 合并**（`1/(i+rank_const)`） | 实读 `search.py`、`search_utils.py` |
| Mem0 | 实体自动抽取，OSS 存入独立集合 `{collection}_entities`；检索声明语义 + BM25 + 实体匹配 | 官方能力声明（权重未核验） |
| mcp-memory-service | tags + 实体链接（`@mentions`/`#tags`/URL/paths）；语义稀疏时**退化到 exact/tag 匹配** | README 声明 |
| Letta | memory blocks 与 archival passages 分层 | 只确认接口存在，检索细节**未核实**（如实标注） |

**术语边界（这一条最有指导性）**：`alias/synonym expansion`（别名/同义词扩展）与
`entity linking`、`tags/keywords`、`query rewriting`、`HyDE`、`RRF` 不是一回事——
**只有第一种是"用户词面直接映射到库内术语"，最贴切也最可审计**；tags/keywords 适合粗召回，
但"规范""技能"这类泛词会误召回；RRF 只是融合算法，**它不生成桥**。

**长内容这一侧**：`resources/read` 在 MCP 规范里**没有分页**（只有 list 操作有 `nextCursor`），
所以分块必须由工具参数自己扩展。可复用的做法：

- **Basic Memory PR #601**：搜索结果加 `matched_chunk`（命中的那一段，而不是文档开头），
  `read_note` 支持 `start_line`/`end_line`，回执带 `total_lines`/`has_more`/`next_start_line`；
- **Graphiti / Cognee**：把事实（约束）与摘要（导读）分层，避免"把摘要当全文"；
- **TACL 2024《Lost in the Middle》**：关键信息在上下文中段时召回跌到 **30% 以下**；
- **Anthropic 长上下文建议**：长文档置顶、查询置底（官方称可提升至多 30%）；
- **Roo Code**：截断时在输出尾部**显式**写 "Showing only X of Y"。

**三条"不要做"**（同一份调研的结论）：不要引入图数据库（几百条用一张自关联表就够）、
不要多层摘要树（两层：文档摘要 + 章节目录）、**不要"必须逐块读完才放行"**——那会让一次排障
变成十几轮往返，反而拖垮回合。

## 三、设计与实现

**术语桥（`src/term-bridge.ts` + 索引接入）**

- 字段：`aliases`（同一种东西的别的叫法）+ `keywords`（这条讲什么）加进 schema 的 `common`，
  于是每种 kind 都带；
- **接入检索的方式是零改动**：`searchable()` 索引的是整条 content 的 JSON，所以桥写进条目就自动
  进全文索引，用户搜别名即可命中原条目，`why.matched` 还会显示是哪个词命中的；
- **桥不写回条目**：写回会造新修订、把历史搅乱。它在索引时算（`withBridge`），所以
  **"重建索引"就等于"刷新桥"**——`amb reindex` 做这件事；
- **概念组而不是中英对照表**：实测撞到的失败是「规矩」↔「规范」这类**同语言的口语差异**，
  只补中英对照救不了；
- **条目自带的 aliases 优先**：模型归纳或人填的比规则更强，规则不覆盖它。

**规范可发现性（`src/store.ts`）**

`hostProvided` 的规范改成**点名 + 给取回方式**，但**不给正文**——宿主已经注入过那份正文，
再发一遍就是重复指令，可能与宿主自己的基线打架（这条由 `skill-context` 的测试钉住，它比
"顺手多给几句"重要）。**不提就等于不存在；只给 id 等于半提；但补正文等于重复。**

**分块读取（`src/retrieval-chunk.ts`）**

- 切法：按 Markdown 标题切 → **合并相邻段到 4000 字符** → 仍超长的按字符窗口切（留 120 字符重叠）；
- 回执：`chunkIndex`/`totalChunks`/`hasMore`/`nextChunkIndex`/`startLine`/`endLine`/`totalLines`/
  **`outline`（目录，用于跳读）**/**`advisory`（明说还有几块未读）**；
- `full=true` 保留旧行为，供导出/审计这类确实需要全文的调用方；
- **查询与分块不并用**：`query` 本身就在缩小范围，再叠一层分块只会让读者分不清在看哪一种。

**合并的两条硬要求**（都是测试先发现的）：块名必须覆盖块内的小节（否则目录骗人——
一个叫「第一节」的块里装着「第二节」的约束）；开头段借后续标题作名字（否则目录里出现 `(开头)`）。

**注入改进**：`excerpt` 从"正文开头 400 字符"改为**与查询相关的段落**，但**总长仍受
`excerptChars` 约束**（那是调用方对注入量的决定，不是实现可以放大的）；注入行写明
"上面只是片段、约几块、怎么读全"。

## 四、验证

- 端到端：「我以前写下的那些规矩」由 `matched=0` 变为命中 2 条 norm；「我定下的那些条条框框」同样命中；
- 41947 字符的技能：由"一次给全文"变为 **16 块**（首版按标题硬切是 52 块），首块 3505 字符，
  目录含真实小节名，回执写明"还有 N 块未读"；
- 测试：`test/term-bridge.test.ts` 4 条、`test/retrieval-chunk.test.ts` 5 条，全绿；
- 全量 828 项 / 826 通过 / 0 失败；契约 43/43（新增 `term-bridge`、
  `host-norms-are-named-not-resent`、`long-entries-are-read-in-chunks`）。

## 五、模型归纳版术语桥（已接）

规则版覆盖不了**个性化**的说法：项目内部黑话、旧称、某个人的习惯叫法。那些要"读过条目、
又见过用户怎么说话"的一方来补——也就是模型。`src/term-bridge-model.ts` + `amb bridge` 做这件事。

三条纪律与向量层同一套：**未配置就明说**（不假装跑过）、**不可用/不合形状降级到规则桥**
（不是"没有桥"）、**产出逐条清洗**。第三条被测试连抓两次：把长度下限放进 schema 会让
**一个坏项作废整批**——`.min(2)` 挡掉单字、`.min(1)` 挡掉 trim 后的空白串，两次都变成
`invalid_response`，而不是"剔掉那个词、留下其余的"。修法是 schema 只管形状，长度交给 `clean()`。

产出落在独立的 `entry_bridges` 表、**不写回条目**：桥是检索辅助，不值得为它造一条新修订。
跑完自动重建索引——与规则桥共用同一条出口，所以"重建索引 = 刷新桥"这句话对两者都成立。

## 六、仍未做的（别把这份文档读成"已经完美"）

- **模型版只在 stub 下验证过**：本机没有配置 `model-review.json`，所以真实模型路径（延迟、
  输出风格、它对中文黑话的实际归纳质量）**没有实测**。要启用：把配置写到该文件，再跑
  `amb bridge --yes`。
- **词法匹配质量本身没变**：盲测精确率 0.381 / 召回 0.727，中文仍是重叠二元组。
- **向量层**默认关闭且未在真实嵌入服务上验证过。
- **仍未测**：并发（reindex 与检索同时进行）、万级条目规模、多进程同时写。
