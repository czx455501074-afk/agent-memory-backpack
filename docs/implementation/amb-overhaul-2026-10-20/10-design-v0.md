## 二、设计目标（可验收）

- **G1 写入即分类**：`kind` + `scope` + `domain` 三字段在落库时确定，缺失不得静默补默认。
- **G2 证据可解析**：至少一条引用能被代码验证存在；不能验证的不得进入自动注入与规范层。
- **G3 层级可用**：域 → 集合 → 条目 → 修订 → 证据 → 关系，能按域检索、能反向列成员。
- **G4 预算受控**：工具定义与注入段有硬上限，且超限时说明省略了什么。
- **G5 覆盖可报**：检索与读取都回答"还缺什么"，agent 能在收尾前自检。

## 三、设计决策

### D1 语义分类：9 种 kind + 受控 domain 词表

把 `memory` 拆开，让"规范/技能/经验/踩坑/事实"各自成类：

| kind | 定义 | 判据 | 典型来源 |
|---|---|---|---|
| `norm` | 必须遵守的规则 | 违反会出错或有明确代价；有适用边界 | 用户明说、AGENTS.md 晋升 |
| `skill` | 可执行的方法体系 | 有入口、有叶子、有触发条件 | 技能目录导入 |
| `workflow` | 有序步骤 | 有前置、阶段、完成判据 | 技能结构化 |
| `experience` | 验证过的做法 | 有适用/不适用、有可复算判据、有证据 | 任务收尾提交 |
| `pitfall` | 失败模式 | 有症状、根因、规避动作、复发条件 | 排障收尾 |
| `fact` | 可核对的状态 | 环境/版本/路径/账号结构，会过期 | 勘察 |
| `journal` | 一次会话的事件 | 有时间线、不做通用断言 | 自动归档 |
| `material` | 外部资料 | 有 URL、有摘要、必然过期 | 抓取 |
| `preference` | 用户取向 | 关于"怎么做"的偏好 | 用户明说 |

`domain`（工作类别）是受控词表，允许受控扩展，初版从真实库归纳后由用户确认；**不允许 agent 自造新域**，只能建议。

**分工**：`kind`/`domain` 的语义归类必须模型介入（规则只能做否决与兜底）；枚举合法性、scope 继承、domain 是否存在、必填与否，全部由代码确定。

**降级**：模型不可用 → 规则分类器给候选 + 标记 `classifiedBy: rules`，该条 `durability=unknown`，不进自动注入，进"待分类"队列。

### D2 证据契约：能验证的才算证据

1. `evidenceRefs` 至少 1 条，按 `kind` 做结构校验：
   - `artifact`：仓库相对路径必须存在（外部绝对路径需在白名单根内）
   - `command`：必须含命令文本 + `exitCode`；可复算性由"重跑一次"验证（可选的 `rerun` 标记）
   - `event`：`eventId` 必须能在事件表查到
   - `knowledge`：`id@revision` 必须可读回
   - `url`：格式校验 + 可选抓取头校验，抓不到标 `unreachable` 而不是失败
2. 全部引用都验证失败 → 拒收（返回结构化错误，指出哪个字段、为什么），不是降级。
3. 自述型证据黑名单：`evidence` 写"已验证/已测试/passed"但无引用 → 拒收。这是伪造证据的高发形态。
4. **自动取证（关键）**：宿主 hook 在每次工具调用后把 `(tool, 参数摘要, exitCode, 时间, sessionId)` 写入事件表；agent 提交经验时引用 `stepId`，代码把真实回执展开为 `command`/`artifact` 引用。**agent 少打字，代码多取证。**

分工：结构校验与回填 = 代码；"这条证据是否支持该结论" = 模型（且模型只能降级，不能升级）。

### D3 层级：域 → 集合 → 条目 → 修订 → 证据

- 新增 `domains`、`collections`、`collection_members` 三表；`knowledge` 表增加 `domain_id` 列（用于索引与过滤，JSON 仍是权威内容）。
- 现有 `curation.members` 保持可读，迁移时双写；集合从 JSON 落到表后，可反向查询"这个域下有哪些条目""这条属于哪些集合"。
- 反对意见先说在前面：**层级不是目的**。只有当"按域预取""按集合遍历""按域统计覆盖度"三者中至少两个有实测收益时才落地；否则只加 `domain` 列，不加集合表。
- 代码可确定性完成全部迁移与索引；无需模型。

### D4 预算：工具面与注入段都要有硬上限

- 工具面：合并读类工具（`search`/`read`/`view` 归一），描述压到一句 + 参数说明进技能文档；目标见 P0 工具面审计的实测基线。
- 注入段：规范已有字符预算（`normBudgetChars`）；补齐知识段预算，并在超限时输出"省略了哪几条、为什么"。
- 技能目录：不再全量进系统提示，改为按需索引（这属于宿主配置改动，需单独评估，不在本插件内擅改）。
- 代码可确定性完成。

### D5 覆盖契约：每次检索都回答"还缺什么"

检索/读取返回统一 `coverage` 结构：

```
coverage: {
  matched, returned, truncated,
  unreadChunks, relatedUnread,
  degraded: 'none' | 'vector-off' | 'index-off' | 'model-off',
  nextAction: 'continue' | 'read-chunk' | 'widen-query' | 'done'
}
```

另加收尾自检工具 `amb_recall_audit`：给定任务目标，多路召回后报告"已覆盖/未覆盖的子目标"。它不承诺穷尽，只把缺口显式化。

分工：多路召回与统计 = 代码；子目标拆解与覆盖判断 = 模型（不可用时退化为关键词覆盖报告）。

## 四、迁移与回滚

- 全部改动向前兼容：新字段可选、旧 JSON 保留、迁移只增量。
- 每个阶段有只读脚本可复算；真实库改动先在副本演练，`integrity_check=ok` 才碰真库。
- 回滚是"向前修订"：恢复旧值作为新修订，不删除历史。

## 五、本轮不做

- 不迁移到图数据库/向量库（现架构够用，先修准确率）。
- 不改宿主系统提示与技能目录加载方式（需用户另行决定）。
- 不重跑上一轮的整理批次。

## 六、待评审问题（交高级模型）

1. `experience` 与 `pitfall` 的边界是否稳定？会不会导致同一结论双写？
2. 证据拒收策略是否过严？会不会让 agent 干脆不提交（沉默失败）？
3. 自动取证依赖 hook 记录工具回执，隐私与体积如何取舍？
4. domain 词表由谁维护？自动扩展会不会退化成标签垃圾场？
5. 集合表是否真有必要，还是 domain 列 + 标签就够？
6. 覆盖契约会不会变成"仪式性字段"，agent 看一眼就忽略？
