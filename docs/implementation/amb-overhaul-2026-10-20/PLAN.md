## 0. 一句话目标

把 AMB 从「能存能搜的记忆插件」改成「写入即分类、分类即带证、检索即报覆盖、注入即守预算」的知识系统；并证明它在真实 DSH/Codex 会话里省上下文、提准确率，而不是把噪声塞回去。

## 1. 用户七问 → 可验收指标

用户原话拆成七问，每问必须有可复算指标，不接受"感觉变好了"。

| # | 问题 | 验收指标（可复算） | 判定 |
|---|---|---|---|
| Q1 | 收获经验但没附证据 | 写入入口的证据字段必填率、证据可解析率（指向文件/命令/会话事件的占比）、`evidence=verified` 必须有可核对回执而非自述 | 100% 入口覆盖；0 条"只写'已验证'"的自述证据 |
| Q2 | 没有结构化归类 | 每条写入必须落定 `kind`（规范/项目规范/技能/经验/踩坑/日记/资料）、`scope`（global/project/task）、`domain`（工作类别）；分类器（规则+模型）一致率与误判率 | 分类三字段缺失率 0；盲测一致率 ≥90%，误判有回执 |
| Q3 | 数据库有没有层级 | 明确 taxonomy：域 → 集合 → 条目 → 修订 → 证据 → 关系；表与索引落地；层级可查询可遍历 | 层级图 + 迁移脚本 + 只读遍历证据 |
| Q4 | 新会话为什么塞 200K | 新会话上下文按来源分解（系统提示/工具定义/技能目录/AMB 注入/项目规范），逐项字符数与估算 token | 分解表 + AMB 自身占比 + 可削减额度 |
| Q5 | agent 会不会拿到无用资料 | 注入段与检索结果的噪声率（人判无关条目占比）、预算利用率 | 噪声率基线 → 目标下降；注入永不超预算 |
| Q6 | 检索是否精准快速 | Recall@K、精确命中保留率、p95 延迟、零结果可解释率 | 有基线、有对照、有复算脚本 |
| Q7 | 是否确认收齐 | 覆盖回执：本次返回类型、总数、已返回范围、未读块、未覆盖子目标、下一步 | 每次检索/读取都带覆盖回执；可区分"真无匹配/过滤后为空/降级" |

## 6. 部署纪律（红线）

1. 顺序固定：停核心 → 部署 → 起核心（`deploy-plugin.mjs` 在核心运行时必然 EBUSY）。
2. 部署前必须有：`npm test` 全绿、`node verification/contracts.mjs` 通过、`node scripts/verify-host-deployment.mjs` 对当前版本给出判定、真实库备份存在。
3. 部署后用真实调用验证（工具可见、带证据提交一次、检索一次、hook 事件流有记录），不看日志自述。
4. 任一验证失败立即回滚到部署前备份，并在本目录记 `06-deploy.md` 的失败事实。
5. 不改变用户数据：迁移只做增量，不删除原件，保留回滚批次。

## 8. 事故与策略调整（19:11）

**事实**：18:45 派出的四个只读审计子代理全部 failed，零产出（`01/02/03/04` 均未生成）。同一时段 DSH Web GUI 端口由 59808 变为 57062，后台 job 句柄失效（`unknown job`），会话出现 `[model changed]` 与任务 paused/续接记录。结论：**宿主进程重启杀死了全部子代理**，不是额度、不是路由、不是权限。证据：重启后单独派出的探测子代理 `CHANNEL_OK` 正常返回。

**副产物（本身即为 Q5 证据）**：一次只输出 `CHANNEL_OK` 的探测任务，在 AMB 里留下了 2 条 journal 记录（`journal-task-13b184610beb0783`，知识版本 222→224），其中一条为空的收尾记录。这说明**自动收尾会把无信息量的会话写成长期条目**，正是用户抱怨的"塞入毫无用处的资料"的一种：噪声不只来自检索，也来自写入侧。

**策略调整**（本工程后续一律执行）：
1. 子代理任务切窄：单一问题、单一产出、预计 10-15 分钟；禁止"审计全部写入路径"这类大包。
2. 每个子代理的第一条动作是创建产出文件并写骨架，之后逐段追加——被重启打断时留下可用进度。
3. 主控承担需要连续推理的关键测量与设计，子代理承担可并行的窄取证。
4. 派完立即登记到本文件 §7，便于重启后按文件核对"哪些已完成、哪些要重派"。
