# AMB 重构设计 v0 对抗评审

评审口径：以 `10-design-v0.md`、`PLAN.md` 与当前源码为准。结论聚焦可证伪的事实和上线后会发生的失效，不把“字段齐全”当成用户问题已解决。

## 结论

当前稿不宜直接进入 P2。主要原因不是方向错，而是把“可解析引用”误写成“可验证证据”，把已存在的调用方分类提示误写成知识条目分类缺失，并把覆盖回执升级成新工具/新模型职责而没有定义可测的准确性。应先修正事实基线与验收口径，再用最小迁移解决写入噪声、分类归档和检索完整性。

## 1. 错误与逻辑断裂

1. **D-1 把 `memoryContext.kind` 当成知识条目的 `kind`。** 设计稿 `10-design-v0.md:11` 声称 `kind` 可缺省；但 `src/schema.ts:206-209` 的 `memorySchema` 将条目 kind 固定为 `memory`，其余 kind 也分别由 schema 的 literal 固定；`src/schema.ts:288-290` 的 `knowledgeSchema` 是各类 schema 的联合。可选的是 `memoryContextSchema.kind`（`src/schema.ts:49-55`），属于候选分类上下文，不是已落库条目的 kind。**动作：**重写 D-1，分别统计“已采纳知识 kind 缺失率”和“提交候选分类字段缺失率”，避免把候选阶段与落库阶段混为一谈。

2. **D-1 将 `memory` 说成事实/状态/经验/踩坑的无差别桶，遗漏了既有角色隔离。** `src/schema.ts:202-209` 定义 memory 为 durable background facts；`src/memory-policy.ts:62-66` 会阻止缺失支持证据的 memory 自动召回；journal 有独立的 `did/problems/outcome/unfinished`（`src/schema.ts:236-253`）。实际问题更像是已归档内容的语义粒度不足和自动归档噪声，不是这些类别完全没有边界。**动作：**先对真实库抽样标注现有条目，统计误分类矩阵；仅将高频且判据稳定的子类拆分，别一次新增九类。

3. **D-2 把“引用存在”误称为“证据可验证”，并用错误字段推导当前事实。** `10-design-v0.md:13` 声称 evidenceRefs 可选、缺失时按 `unverifiable` 落库；`src/schema.ts:62-72` 只定义引用结构，`src/schema.ts:73-82` 的 support 是证据捕获封装，`src/evidence.ts:10-20` 明确只冻结调用方提供内容、脱敏、算哈希，不访问网络或文件，也不升级声明。另 `src/schema.ts:104` 是 `support` 可选，不等价于 `evidenceRefs` 字段本身。**动作：**将问题表述为“候选可提交零引用、采纳时可能记录 missing support”，并把“结构有效、引用可解析、命题被支持”拆成三个不同判据；哈希仅证明快照一致，不证明命题真实。

4. **D-3 把知识库结构概括为只有两张表，忽略现有事件、提案、任务、派生关系等表。** `10-design-v0.md:15` 对 knowledge 与 revisions 的描述基本准确，但它不能推出全库“扁平、无关系”；`src/store.ts:804-806` 已有 events，且附近建有 proposals、tasks、outbox、supersessions、entry_bridges 等结构（如 `src/store.ts:862-872`、`src/store.ts:892-900`、`src/store.ts:3612`）。**动作：**将 D-3 限定为“知识条目与集合成员目前主要内嵌 JSON”，附全库 ER 草图，不以全库扁平作为三表迁移理由。

5. **D-6 的“不可反向查询”没有证明。** `10-design-v0.md:17` 说 members 无成员表、不可反向查询；`src/store.ts:1767-1773` 可返回 curation.members 的投影，且 `src/store.ts:4014-4070` 已实现批次应用、来源约束、成员检查等。缺少专用索引表不等于绝对不可查，只是需扫描 JSON 或受既有查询接口限制。**动作：**给出实际查询需求、当前可行查询及实测代价；只有实际延迟或功能缺口成立才建关系表。

6. **D-7 把“宿主已加载规范不重复注入”判作口径错误。** `10-design-v0.md:17` 的“规范 0 条”应区分“库中登记数”与“本次新注入数”；`src/store.ts:2067-2072` 明确宿主已有规范仍留在索引与审计中，但不会重复注入。这是设计选择，不是错误计数。**动作：**自检输出拆成 `registered`、`hostProvided`、`injected` 三项；无需因“0 条注入”改动注入语义。

7. **D-8 仅凭一次探测不能归因“自动收尾写入零信息 journal”。** `10-design-v0.md:18` 报版本 222→224 与两条 journal，但该观测只能证明同一时间窗发生两次知识版本写入；不能单独证明两个条目都来自自动收尾，更不能证明全体自动归档都无信息。`src/memory-policy.ts:25-46` 有噪声/事件启发式，但应用位置与保留策略仍需追踪。**动作：**以 `taskId`、origin、journal 内容和 `generateJournal` 回执逐条归因；补充至少一组“仅确认消息”与一组有实际产出的对照测量。

8. **D1 的“模型必须分类”与“代码确定性完成分类”边界不成立。** `10-design-v0.md:48-50` 让模型给候选、代码标 unknown 并进待分类队列，但 kind/domain 的误判仍会影响路由；此外 `durability=unknown` 是否存在于正式 schema、哪个字段承载、入库后如何拦截自动注入均未指定。`src/memory-policy.ts:10-18` 的 assessment durability 有 unknown，但不是所有知识 schema 的通用持久化字段。**动作：**定义持久化字段与默认召回门禁；模型输出只作为候选，未知分类必须维持可搜索、不可自动注入、可人工确认，且设定队列清理/提醒策略。

9. **D2 所谓“重跑命令”不能作为通用证据验证器。** `10-design-v0.md:56-59` 对命令回执建议重跑；命令可能有副作用、依赖变化的工作区/网络/时间或已过期凭据。event ID 可查到只证明事件存在，不证明事件内容足以支撑结论；artifact path 存在也不证明内容与提交时一致。**动作：**默认校验不可变回执（事件摘要、时间、digest、退出状态）；命令重跑仅允许显式标记、隔离夹具与无副作用白名单，严禁通用自动重放。

10. **D4 以“合并 search/read/view”为工具面降本方案，但未给宿主实测基线与兼容成本。** `10-design-v0.md:75` 的目标依赖 P0 工具审计，而相关审计文件尚标“进行中”（`01a-amb-tool-surface.md:1-12`）；MCP 工具 schema 与 DSH 原生工具定义各有注册点，仓库规范也明确两处都要改。**动作：**先对 DSH 与 Codex 分别量出定义 token、调用频率、误调用率；只有语义统一且减少总 token 才合并，否则只压缩描述、保留稳定工具名兼容。

11. **D5 的 `unreadChunks`、`relatedUnread`、`degraded` 字段无统一定义。** `10-design-v0.md:82-90` 混合了分页、关联检索、向量/索引状态；`src/store.ts:2215-2323` 已有 considered/shown/hint/gaps/withheld/selectionBasis 等检索回执，`amb_read_knowledge` 的 chunk 读取则是另一种覆盖口径。**动作：**按 search、read、prepare 三种操作分别定义计数和真值来源；没法由当前操作证明的关系缺口一律为 `unknown`，不得用一个 coverage 对象制造表面统一。

## 2. 過度设计與更省替代

1. **一次性新增九类 kind。** 成本：900 条真实数据的重分类、旧 kind 兼容、每个入口/注入/筛选/备份/导入/测试的分支扩张；分类边界会迅速变成长期治理负担。替代：保持现有稳定 kind，先增加可选、非权威的 `category` 或候选分类记录，只拆分“经验/踩坑”中经盲测证明可稳定区分的少数类；确认收益后再做正式迁移。

2. **`domains`、`collections`、`collection_members` 三表同时引入。** 成本：从内嵌 JSON 双写引入一致性故障、回滚与导入导出复杂度、SQLite 迁移测试矩阵；对每条查询都要处理双源权威问题。替代：先加一项可选 domain 到 JSON/索引投影，保留 `curation.members`，用现有 JSON/FTS 查小规模库；按域查询若实测慢，再物化单一 `collection_members` 表，明确唯一写入源与重建脚本。

3. **每次工具调用保存参数摘要、退出码、时间、sessionId 并展开成证据。** 成本：事件量按调用数线性增长，敏感参数、提示注入载荷、文件路径及工具返回可能进入持久化；摘要规则会造成漏证或不可逆隐私泄漏，hook 失败还会扩大宿主关键路径。替代：复用现有事件流，仅记录低敏元数据和 content hash；默认不保存参数/结果正文，用户显式对单个任务开启采样，并设置按项目、类型、字节数、TTL 的硬预算与删除/导出能力。

4. **新增多路模型召回 `amb_recall_audit`。** 成本：又一个工具定义、一次高延迟/高 token 模型调用、子目标拆分误差，以及“模型觉得覆盖了”造成虚假完备。替代：先扩展现有 prepare/retrieval receipt 的可计算字段；用户要求收尾盘点时，以任务 checklist/目标拆分作为显式输入，输出“命中/未命中/无法判断”，不宣称自动穷尽。

5. **“每条知识都必须有可验证引用”作为硬拒收。** 成本：用户偏好、计划、暂定假设、工作中观察等本来就可先存线索；强制门槛会提高提交摩擦、让沉默失败变成数据缺失。替代：分层接收：无证据可保存为 `self-reported/unverified` 候选且禁自动注入；存在可读回回执才允许标 `observed/verifiable`；规范层另设人工确认门槛。

## 3. 低估的风险与最坏情况

1. **证据拒收导致静默不提交。** 最坏情况：agent 连续遇到无可引用证据的经验，遇到结构化 4xx 后放弃提交；用户只看到“记忆库没记住”，而系统日志只记拒收、不产生候选，问题复发且没有可追踪线索。触发：远程 URL 不可达、事件已过期、路径不在当前 checkout、MCP schema 不允许引用新类型、host hook 未送达。处理：拒收改为显式三态 `accepted-unverified / needs-evidence / accepted-verified`；任何失败都在任务回执可见并放入限期候选队列，需明确显示写入状态和重试入口，不得静默丢弃。

2. **自动取证把工具流水灌进知识库。** 最坏情况：每次读取文件、浏览网页、调用工具都生成事件快照，带入凭据、私密文本、巨大响应；长期压过规范与技能的检索排序，形成比当前自动 journal 更大的污染面。触发：所有 tool call 默认采集、参数摘要实际保留正文片段、TTL 仅清事件表而事件已被 journal 引用、重试/两个宿主重复上报。处理：事件与知识分表；只留 allowlist 元数据、稳定去重键与哈希，默认不捕获参数/结果；每任务事件预算与 30 天上限；仅由明确用户动作将选中事件升级为证据。

3. **domain 词表退化为标签垃圾场。** 最坏情况：新增同义、粒度混乱、项目专属词和模型幻觉域，查询必须先猜词表用词；900 条知识被切成大量空域，域覆盖率数字看起来完整却失去检索价值。触发：允许多个角色自由提议、没有合并/弃用规则、域名不设父子或粒度规范、导入与手工写入绕过校验。处理：首版固定少量顶层域；新增域须有定义、反例、近义词、负责人和迁移映射，经人工审核；每季度按使用量合并低频域，不把 domain 当作安全/权威边界。

4. **覆盖契约退化为仪式字段。** 最坏情况：agent 看到 `nextAction=done` 就停止检索；而字段只根据 token 命中计算，未覆盖的子目标、分页遗漏或语义同义问题全被隐藏，错误答案带着“已覆盖”回执。触发：以模型子目标自评代替真实计数、coverage 不携带检索过滤条件/索引状态、read 的 chunk 与 search 的总条数口径混用。处理：只报告可证明事实（候选总数、返回数、游标、未读 chunk 数、实际降级路径）；“子目标覆盖”必须引用明确目标清单并保留 `unknown`，不得默认 done；用盲测召回率/误报率验证回执是否改善行为。

5. **增量迁移与双写并非天然可回滚。** 最坏情况：表关系与 JSON 双写在一次崩溃中不一致，反向查询少条目；继续写入后回滚只恢复旧 JSON，却无法解释新表事实。触发：两处写操作不在同一 SQLite transaction、旧客户端只读旧 JSON、新旧版本并发运行。处理：单事务双写、可重建派生表、迁移版本锁、迁移后全量对账（集合成员双向差集为零）；兼容窗口内仅旧 JSON 为权威。

## 4. 对用户六问的遗漏

计划把问题拆为七项（`PLAN.md:11-23`），用户提出的六问在设计稿中仍有缺口：

1. **证据缺失：**只定义提交入口拒收，没有定义现存 900 条无引用知识如何处理、按可信度分层、旧条目能否继续检索、何时补证和补证失败后的处置。需提供只读盘点指标、迁移队列与不会批量误升级的规则。
2. **无结构归类：**只给 kind/domain 名词和“模型介入”，没有分类决策表、互斥优先级、低置信度/多类条目处理、盲测样本集、误判成本与人工纠正闭环。需用现有库盲测，达不到阈值就只做建议字段，不自动改写权威 kind。
3. **无层级：**未定义 domain 与 collection 的基数、集合是否可嵌套、条目多域/多集合语义、关系类型及删除/归档行为；G3 写了“关系”，D3 却没有关系表或关系查询契约。需明确最小可查询图与实际查询用例，不能只画箭头。
4. **200K 上下文：**稿件只谈插件工具定义与 AMB 注入，没有回答 Q4 的来源拆分、基线、token 估算口径、DSH/Codex 两宿主差异，也没指出 200K 是否由技能目录/系统提示主导。P0 的 `01b-session-payload.md` 仍是待补数据。需先完成分来源、同一会话口径测量，再决定 AMB 能承担多少削减。
5. **检索噪声：**没有定义人审样本、噪声率分母、Recall@K、精确命中保留率、延迟和向量降级对照。新增 domain 可能只改变切片，不保证排序更准。需复用同一夹具与预算跑基线/改后，并报告误注入与漏召回。
6. **无法确认收齐：**coverage 字段与 recall audit 没有把“召回条目数”“全文读取完成”“目标子项覆盖”“库中不存在”区分开，也没有为 MCP 分页、chunk、过滤、索引不可用定义负面状态；用户看到 done 可能仍只是样本。需拆成可证明的返回/未读事实与不可证明的语义覆盖判断，并允许 unknown。

## 5. 第六节六题逐条结论

1. **experience 与 pitfall 边界：修改。** 两者可区分为“正向可复用做法”与“失败机制及规避”，但现实记录常同时包含成功修复和失败根因，强制互斥会诱发双写。保留一个主条目，支持 `pitfall` 作为 experience 的关系/子类型或同条目的“失败模式”章节；只有不同适用边界、独立生命周期时才拆成两条，并互相链接。
2. **证据拒收是否过严：修改。** 拒绝将无证据声明升级为已验证条目是对的；拒绝任何无引用候选则会沉默丢失。实现三态接收与明确回执：候选可先保存为未核实、默认不自动注入；验证层/规范层要求强证据与人工确认；失败必须落待办/重试状态。
3. **自动取证隐私与体积：否决“每次工具调用后保存参数摘要”的默认方案。** 事件量、敏感数据和噪声收益比不成立。保留现有有限事件机制，默认仅记录 allowlist 元数据；正文级采集须显式 opt-in、逐任务限额、TTL、可删除，并由用户选择事件提升为证据。
4. **domain 词表维护：修改。** agent 只能提议是合理的，但“受控扩展”仍缺流程。首版冻结小词表，人工维护唯一词典；每个域要求定义、边界例、别名、负责人、弃用映射；模型不得创建/自动迁移域。以未知域率、域内检索噪声和低频域比例作为治理指标。
5. **集合表是否必要：否决当前三表一次落地。** 设计自身 `10-design-v0.md:70` 已设“至少两个场景实测收益”门槛，但尚无测量证据。先用 domain 列/JSON 与现有成员数组验证按域预取、按集合遍历、统计覆盖度的真实需求；满足任两项且规模/延迟达阈值后，只物化必要的一张成员关系表，并用派生表可重建保证可回滚。
6. **覆盖契约会否仪式化：修改。** 统一结构本身有价值，但 `nextAction=done` 与模型子目标覆盖会造成虚假完整感。将覆盖回执限定为可复算事实，动作只给建议不代替判断；收尾审计必须以用户/任务显式目标清单为输入，逐项标 covered / missing / unknown，且 unknown 不可折叠为 done。用盲测检查 agent 是否真的按回执继续检索。

## 6. 只能做三件事时

1. **先止住自动写入噪声并让提交状态可见。** 对低信息量 journal/工具事件设确定性门槛、默认关闭高噪声正文采集；所有候选明确回执“已保存/待证/失败待重试”。它直接解决无用资料注入与沉默丢失，是知识质量的源头杠杆。
2. **建立可追溯但不伪称真实的证据分层。** 使用已有 support/event 结构，统一 `missing/referenced/captured` 与 `observed/verifiable/self-reported/unverifiable` 的区别；为旧数据盘点和新写入设回执，不以“locator 存在”升级可信度。它能在不重构数据库的情况下阻止自述变规范。
3. **让检索覆盖回执可复算并做盲测。** 先扩展已有 `considered/shown/gaps/withheld/hint` 与 chunk continuation 的准确性；固定查询集，测 Recall@K、噪声率、p95 与分页未读。它直接回应检索噪声和“是否收齐”，并能为 domain/集合是否值得做提供数据。

其余推迟：九类 kind、完整受控 domain 服务、三张层级表、自动工具回执持久化、模型驱动 recall audit、工具合并。它们都增加迁移/兼容/测试面；在三项基础指标未建立前无法证明收益。尤其 200K 问题需先完成 `PLAN.md:20` 的来源测量，若主要来自宿主技能与系统提示，AMB schema 改造并不能直接解决。
