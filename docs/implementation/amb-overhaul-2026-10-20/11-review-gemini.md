- 评审视角：独立对抗评审者（对抗破局视角，聚焦真实多轮 Agent 会话与工业级生产执行）
- 被评审对象：`docs/implementation/amb-overhaul-2026-10-20/10-design-v0.md`

## 重点一：写入侧门禁（kind+scope+domain 必填，证据必填且可解析）

### 1. 判断
**必然导致双向恶化：前期高频报错中断任务，后期 Agent 学会编造虚假结构应付门禁。**
强制要求 Agent 在调用工具时手动拼装完整、可解析的结构化证据和分类，严重背离了大模型输出的不确定性本质。Agent 在遇到 400 校验阻断后，为了完成“收尾落库”的指令，绝不会停下来深思，而是会迅速采用最低成本对抗策略：要么选择极端沉默（“本次无可复用经验”），要么编造形式合规但实质虚脱的证据（随便挂一个刚才执行过的 `git status` 或 `pwd` 当 command 证据；盲选一个存在的 domain）。硬门禁拦截了真实但非结构化的经验，却放行了精致的伪证。

### 2. 触发失败的具体场景
- **场景 A（纯逻辑/代码认知型经验无处安放）**：Agent 在排查并发竞争时，通过代码审查发现了某个异步死锁逻辑并修复。此时没有独立的“测试产物文件”，也没有特定能重跑报错的 CLI 命令。Agent 意图总结这一通用避坑逻辑，但因为必填 `evidenceRefs`，且 `artifact` 强校验文件真实存在、`command` 强校验命令与 exitCode，Agent 无法提交，被 API 抛出 400 拒绝。在重试 2 次失败后，Agent 放弃落库，关键架构经验直接丢失。
- **场景 B（形式过关但毫无意义的应付性提交）**：Agent 为绕过 `evidenceRefs` 校验，直接提取会话历史中最后一次任意工具调用（例如 `cat package.json`，exitCode 0）填入 `command`，domain 填入 `general`。代码层校验该命令合法且 exitCode 吻合，校验通过并落库。结果系统收获了一条证据链完全脱节的垃圾条目。

### 3. 可执行改法（兼顾“不噪声”与“不沉默”）
1. **自动取证成为唯一主干，剥离 Agent 手写证据对象的职责**：
   在 `amb_submit_experience` 工具入参中，彻底废除让 Agent 手写 `evidenceRefs: [...]` 复杂对象的定义。Agent 仅需传递结论描述，或者可选传入关联的 `toolStepId`；证据的采集、结构化封装与 Hash 计算，全部由宿主 Hook 依据会话真实产生的 Tool Execution Trace 自动回填。
2. **设立暂存观察池（Staging Buffer），严禁硬报错拒收**：
   对于未附带可核对证据或分类置信度不足的提交，核心服务端一律返回 `status: "staged"` 接受存储，将其隔离在 `staging` 待定池（标记 `scope: task`，`durability: uncertain`）。这类条目**绝对不进入跨会话全局注入**，只作为单任务参考事实，直到后续有真实运行证据复算验证后再提升为长期条目。
3. **Domain 词表实行服务端弹性容错归一，禁止盲目报错**：
   Agent 传入的 domain 文本若未完全匹配受控词表，由服务端运行规则/嵌入做就近归一，未命中时自动归入 `unclassified`，由离线整理任务处理，切断 Agent 因格式阻断而产生的恶性幻觉。

## 重点二：读取侧设计（coverage 结构的有效性）

### 1. 判断
**无法改变 Agent 行为，必定被 99% 的 Agent 直接视作旁白并忽略。**
在真实自主运行中，Agent 决定是“继续检索”还是“开始干活”的触发器不是元数据里的字段，而是当前 Prompt 里的信息是否足够让它开始输出下一步代码或回答。在返回的 JSON 里塞一个 `coverage: { truncated: true, nextAction: 'continue' }`，但同时把检索到的前 3 条内容全文展示出来，Agent 的注意力会瞬间被这 3 条内容吸走，直接进入方案设计与编码阶段，把外置的 coverage 视为可有可无的调试信息。

### 2. 触发失败的具体场景
- **高危规避项漏读引发生产故障**：用户要求重构某个数据库迁移流程。Agent 调用 `amb_search_universal`，库中命中了 10 条历史经验，第 1 页返回了 3 条通用的操作指南，而第 7 条是致命的“某版本下并发迁移会死锁且不可回滚”的严重踩坑记录（pitfall）。虽然检索响应中带有 `coverage: { matched: 10, returned: 3, truncated: true, unreadChunks: 2, nextAction: 'continue' }`，但 Agent 看到前 3 条操作指南后判定“资料已齐全”，立刻开始编写脚本并执行，最终在测试库引发死锁。

### 3. 可执行改法（必须怎么设计才会被 Agent 真正使用）
1. **在正文流末尾注入强阻断提示文本（Prompt-level Barrier）**：
   不要只把覆盖信息放在 JSON 的独立字段，必须将警示语直接拼接到注入文本的末尾：
   `\n[AMB 覆盖警示：仅返回 3/10 条，尚有 7 条历史经验/避坑未读。当前任务包含未读高危规避项，严禁直接执行写操作，必须调用 amb_search_universal(offset: 3) 续读]\n`。
2. **截断状态下强制实行“摘要目录-按需展开”两阶段返回（Two-phase Unroll）**：
   当 `matched > returned` 且发生截断时，第一页**禁止直接返回前几条的全文**。改为返回这 10 条的精简大纲清单（ID + 标题 + 类别 + 风险等级），要求 Agent 必须根据大纲主动调用 `amb_read_knowledge(id)` 读取感兴趣或高危的叶子正文。切断 Agent 依赖单页半截正文直接脑补的路径。
3. **关键写操作前置覆盖度门禁（Pre-Execution Coverage Gate）**：
   在适配器的 `tools/pre-execute` Hook 中建立软拦截：若当前任务生命周期内触发了截断的知识检索，但在未读完关键条目且未显式调用 `amb_read_knowledge` 确认的情况下直接发起文件修改（`edit`/`write`），门禁拦截并报警：“检测到有未阅读的规范/避坑项，请先确认阅读或传入 force 绕过”。

## 重点三：上下文预算（把“技能目录不进系统提示”列为本轮不做）

### 1. 判断
**这是致命的避重就轻；跳过它将使本次“上下文预算”重构沦为自娱自乐的局部修补。**
新会话上下文动辄 150K~200K tokens 的核心罪魁祸首，正是 DSH 或宿主在启动阶段一股脑全量载入的技能目录（SKILL.md 汇总与各类工具定义 inputSchema）。AMB 注入的规范和历史记录通常只有数千字符（在 1K~3K tokens 量级）。即使将 AMB 自身的注入压缩 50%，在面对 200K 的初始洪流时，节约比例甚至不到 1%。只要技能目录与工具面依然全量硬塞，上下文窗口被稀释、模型指令遵循劣化（lost in the middle）、API 调用成本暴增的根本矛盾就完全没有被解决。

### 2. 触发失败的具体场景
- 用户开启一个新任务会话，DSH 将全局近百个技能的入口描述、数十个 MCP 工具定义全量注入，初始上下文立刻高达 180K。此时系统准备执行 AMB 的 `amb_prepare`。即使 AMB 恪守设计预算，仅注入了 1,500 字符的规范，但大模型面对长达 180K 的上下文早已产生严重的注意力盲区，完全无视了 AMB 刚刚注入的硬规则，继续犯下曾经踩过的低级错误。用户看到会话一开始就吃掉 180K 上下文且 Agent 不听招呼，直接认定重构失败。

### 3. 可执行改法（动作级解决方案）
1. **强制执行上下文来源构成账本审计（Context Attribution Audit）**：
   在 P0 阶段立即落实现实测量脚本，生成精确的上下文分解表（系统底模 Prompt、Tool Schema、Skill Catalog、AMB Context），以事实数据证明 200K 中各部分的精确开销，杜绝模糊推诿。
2. **AMB 插件工具面激进收敛（Tool Consolidation）**：
   即便不动宿主技能加载器，AMB 自身必须带头自降开销。目前 AMB 注册了近 10 个独立工具，其 JSON Schema 在每次交互中都在常驻消耗 Token。必须将读类工具（`search_universal`, `read_knowledge`, `read_stage`）合并为一个统一查询工具 `amb_query`；将写类工具收敛为一个 `amb_mutate`。直接削减 60% 的工具定义常驻体积。
3. **在插件可控配置内实现技能索引轻量化（Index-Only Skill Reference）**：
   对于归入 AMB 知识库管理的 `skill` 条目，严禁在 `prepare` 阶段自动注入全文，仅允许注入单行别名索引（`<id>: <name> | <brief>`）。若需使用，由 Agent 按需调用读取。同时在项目中配置专门的技能白名单子集，拒绝全局全量扫盘注入。

## 重点四：分类体系（9 种 kind 是否过多与边界混乱）

### 1. 判断
**9 种分类显著臃肿过界；核心边界严重混淆，必然导致存储混乱与检索漏检。**
在真实多轮会话中，无论是模型还是人类，都无法稳定界定：
- `experience`（验证过的做法）与 `pitfall`（失败模式）：本质是同一枚硬币的正反面。任何有效的踩坑记录，必然伴随着规避做法；任何经验，本质都是从既往失败中总结出的有效路径。强行拆分只会导致要么双写，要么 Agent 随机乱抛。
- `fact`（可核对的状态）与 `material`（外部资料）：静态环境事实（如端口、版本）与从外部提取的材料事实边界极度模糊。
- `skill`（可执行方法体系）与 `workflow`（有序步骤）：完全是人为制造的抽象裂痕，代码还为此设计了繁琐的“技能结构化为工作流”的状态机，增加了不必要的维护负担。

### 2. 触发失败的具体场景
- Agent 在解决“Node.js 24 下 SQLite 模块编译错误”后，提交了一条 `pitfall` 记录（标题：“Node 24 node-gyp 编译不兼容”）。而在随后的另一个会话中，新 Agent 遇到了类似编译任务，它调用了 `amb_search_universal(kind='experience', query='Node 24 sqlite')` 试图寻找解决方案。由于检索被显式限定了 `kind='experience'`，那条原本能救命的 `pitfall` 记录被完全过滤掉。Agent 只能重复踩坑、编译报错。过度细分的 kind 成了人为制造的信息隔绝孤岛。

### 3. 可执行改法（建议的最小可用正交集合）
将 9 种分类收敛为 **4 种核心类别 + 1 种归档类别**：

| 推荐分类 (Kind) | 覆盖的原分类 | 核心定义与正交判据 |
|---|---|---|
| **`rule`** | `norm`, `preference` | **硬性约束与取向**：执行中必须无条件遵从的红线、代码风格、环境限制或用户明确偏好。违反即导致任务不合规。 |
| **`lesson`** | `experience`, `pitfall` | **因果经验与避坑**：内部必须采用统一的“**场景条件 (When) + 错误做法/陷阱 (Trap) + 正确做法 (Action) + 验证结果 (Proof)**”四元组结构。彻底消灭踩坑与经验的人为割裂。 |
| **`state`** | `fact`, 局部内部状态 | **客观事实与环境基线**：当前系统、仓库、架构的静态或半静态事实（端口、版本、路径、账号架构）。只描述客观存在，不包含操作指令，具备过期属性。 |
| **`reference`** | `material` | **外部参考与引用材料**：外部抓取的文档、API 参考、网页摘要，必须携带 source URL 与拉取时间戳，不作为系统主观规范。 |
| **`journal`** | `journal` | **事件流水与审计台账**：单个任务的执行过程流水账与未完成清单，仅作为排障与任务交接上下文，永不晋升为系统通用经验。 |

*(注：原 `skill` 和 `workflow` 不再作为原子条目的 kind，而是作为上述条目按特定主题聚合的“集合（Collection/Pack）”，通过集合关联，不再污染原子条目的元类型。)*

## 你认为设计稿最该改的三处

1. **废弃 Agent 手填结构化证据的硬性门禁，改为“Hook 自动捕获 Trace + 存入 Staging 待定池”**：
   不要用 `evidenceRefs` 的严格校验阻断 Agent 的提交动作。Agent 只负责阐明事实结论，证据由适配器层从真实工具调用链中自动抓取；未达标条目不报错拒收，而是降级隔离在 `staging` 池，防范模型因格式挫败而演化出虚假对抗。
2. **将 coverage 从静态 JSON 旁白，升级为“正文阻断警示 + 截断时强制目录展开”**：
   彻底消灭只存在于元数据层面的 coverage。只要检索发生截断，正文末尾必须强制注入加粗的大模型阻断警示；且在截断场景下只返回大纲，逼迫 Agent 必须主动调用 `amb_read_knowledge` 展开关键项，使覆盖感知具备执行约束力。
3. **将 9 种臃肿的 Kind 收敛为 4+1 极简正交体系（`rule`, `lesson`, `state`, `reference`, `journal`）**：
   坚决将 `experience` 与 `pitfall` 合并为因果四元组的 `lesson`，消除信息孤岛和多重提交，从根源上降低 Agent 的分类认知开销，避免因分类过滤导致的漏检。

## 你认为设计稿最好的两处（说明为什么，别客套）

1. **提出 D2-4 自动取证机制（“Agent 少打字，代码多取证”）**：
   这是整个设计中最具备实战洞察力的闪光点。作者准确抓住了“大模型在高强度多步执行后不可能保持严谨形式化输出”的人性与模型弱点，提出由宿主在每次工具调用后自动写事件表、Agent 仅需引用 stepId 的方案。这个方向是从“纸面架构”走向“工业落地”的唯一正道。
2. **对层级模型保持高度冷静与克制（D3 明确反对为建层级而建层级）**：
   在几乎所有知识库设计都盲目追求图数据库、深层知识树的行业通病下，设计稿明确指出“层级不是目的”，并立下硬规：“只有当按域预取、按集合遍历、按域统计覆盖度至少两个有实测收益时才落地集合表；否则只加 domain 列”。这种以实测收益为准绳、坚决拒绝过早抽象的务实态度，非常难能可贵。
