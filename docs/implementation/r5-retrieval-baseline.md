## 三、这张表说明三件事

**3.1 拦住规范的是候选集排除，不是排序公式。**

Q1/Q2 里"含 norm"的分数分别是 **4.27 / 2.83**，把第二名（0.66 / 0.94）甩开一个身位。也就是说：**排序本身已经能把规范排到第一**，只要它进入候选集。这直接推翻了"长文档占优是首要问题"的假设——`coverage = idfSum(hits)/presentIdf` 确实对长度不敏感地偏向短文档，但它在当前数据上没有构成拦截。

**3.2 负对照必须留着。**

Q3 证明改动没有把"库里没有的东西"硬凑出来；含 norm 前后几乎不变，说明没有引入新的假阳性。**任何后续排序改动都要把 Q3 当作回归哨兵。**

**3.3 注入回执在自证其伪。**

同一次 `prepare`（Q1 的查询）返回：

```
tokens: 13
matchedTokens: []          ← 空
gaps: [打包, 包脚, 脚本, 本必, 必须, 须包, 包含, 含全, 全量, 量语, 语法, 法扫, 扫描]   ← 13/13 全列
selected: []
norms 已注入: [norm:endpoint, norm:log-wind, norm:package-, norm:timeout-]
budget.usedChars: 594 / 12000
```

**规范明明注入了，检索回执却说一个词都没命中、并把全部 13 个词报成缺口。** 这条错误信号会让 agent 与用户同时误判"库里没有这方面的知识"，也是"漏检"这一进化信号不可用的直接原因。归属 W1 追加 A。

## 四、验收口径（W1 完成时必须给出这四行）

1. Q1/Q2 在**索引路径**（不再排除 norm）能命中对应规范，且顺序与上表"含 norm"一致；
2. Q3 的行为不发生实质变化（负对照不退步）；
3. 同一次 `prepare` 的 `matchedTokens` 非空、`gaps` 不再包含被命中规范提供的词；
4. 同一查询从"注入入口"与"显式检索入口"得到同一结论（`local_index:` 前缀的原因串允许保留差别，结论不许不同）。

### 4.1 口径修正（2026-10-17 收口时发现，重要）

第 3 条**必须模拟宿主的真实调用**：`/v1/prepare`（`src/server.ts`）在"选择不属于未配置情形"时会把 `selectedIds` 转发给核心，因此验收脚本也要先跑一次检索服务、再带着选择去调 `prepare`。

这条修正的由来：首版验收脚本直接 `prepare(projectId, query, {})` 空调用，于是拿到 `回执诚实 FAIL`；按宿主口径重跑后为 **PASS**。**同一次修复，两种判据给出相反结论**——如果当时直接采信 FAIL，就会去改一个已经正确的实现。已修：`scripts/r5-acceptance.mjs` 现在先取选择再转发（与 `src/server.ts` 一致）。

### 4.2 仍然存在的边界（未修，如实记录）

当 `selectedIds` 为**空数组**时（例如查询被判为"状态汇报"或"无正向任务"而提前返回），核心仍按"有选择"处理：`matchedTokens` 为空、`gaps` 列出全部查询片段。现实影响有限（这类查询本就没有检索意图，`gaps` 不会被当成漏检），但语义上不干净——`gaps` 的含义是"库中没有这个片段"，而这里其实是"本次未做选择"。列为待修项。
