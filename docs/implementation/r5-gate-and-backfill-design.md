# B1–B3 实施方案（设计，待实施）

三个发布阻塞项的实施设计。写在前面的原因：这一轮已经因为"边想边改"踩过一次（断言固化了缺陷），先把形状定下来再动手。

## B1：审核门禁改由服务端强制

**现状（已核实）**：`src/server.ts:491-505` 的 `/v1/proposals/approve` 只校验 `entry`、`allowGlobalScope`、可选的 `prefillSource`，**完全不看分类判定**；门禁只存在于 `adapters/dsh/index.mjs:706`（且 `=== false` 判定使字段缺失落入放行侧）；网页界面的单条批准（`src/ui.ts:810`）与批量批准（`src/ui.ts:1345`）都不查。

**设计**：

1. 服务端在 approve 前读该候选的 `classification`，分三种情形：
   - `autoPromotable === false` → 需要请求方提供 `classificationAcknowledged: true`（新可选字段），否则拒绝并说明原因（取自 `promotionBlockedReason`）。
   - **字段缺失** → 同样需要 `classificationAcknowledged: true`，理由写明"该候选的判定来自旧版本判定器，无法据此自动放行"。
   - `autoPromotable === true` → 行为不变。
2. **缺失不等于放行**，这是本次的核心：缺失是"必须由人确认"的理由，而不是"没有异议"的证据。
3. 拒绝的响应要能被人读懂：包含**为什么**需要确认、以及**怎么做**（补一个显式确认字段并重试），不能只回一个错误码。
4. 请求体新增字段是**可选**的，因此现有调用方不会因为缺字段而 500；但缺字段时**会得到拒绝**——这正是设计意图。
5. 客户端配合：网页界面的单条与批量入口各自在人工确认后显式带上该字段（界面上把 `promotionBlockedReason` 显示在按钮旁，而不是藏在详情里）；批量入口若批中混有需确认的候选，要逐个确认或明确告知有几条需要确认，不能静默整批提交。
6. DSH 适配器的 `=== false` 判断改为调用同一语义（或直接依赖服务端返回），避免两处判定漂移。

**测试（三条入口各一）**：

- 适配器路径：一条 `autoPromotable === false` 的候选，经适配器采纳被拒；
- 网页单条：`approveProposalForm` 在未确认时被服务端拒绝、确认后成功；
- 网页批量：批中含需确认项时不得静默通过；
- 另加两条边界：字段缺失时必须要求确认；带确认字段时可正常采纳（证明不是一刀切禁掉）。

**风险**：会改变现有行为（此前能一键采纳的候选现在需要多一步）。这是**有意的行为变更**，必须写进 CHANGELOG 与 README，不能静默。

## B2：存量候选的分类判定回填

**现状**：`payload.classification` 是提交时的快照；库里 360 条待审仍有 255 条标 `norm`（当前分类器重算应得约 13 条）。

**设计**：

1. 新增管理端点（或 CLI 子命令）`proposals/reclassify`：
   - **默认 dry-run**：只返回 before/after 分布与前若干条的变化明细，不写库；
   - `apply: true` 才写。
2. 重算必须**复用提交路径上的同一个分类器函数**（`src/semantic.ts`），不允许另写一套判定——两套判定必然漂移，这正是本项目已经在别处踩过的坑。
3. 写入时同时记 `classifierVersion`（放进 `payload.classification` 内）。这样下次分类器再变时，"哪些判定已过时"是一个可查的查询，而不是又一轮静默的新旧混用。
4. 幂等：判定器版本与文本都没变则跳过，并报告跳过数。
5. **不覆盖审阅人的决定**：只重算仍处于 `pending` 的候选的**判定字段**，不动 `state`、不动 `discovery`、不动任何已采纳条目。

**验收判据**：给出回填前后的只读分布对比（`kind` 分布、`autoPromotable` 分布）；重跑一次 dry-run 应报告"全部跳过"（幂等证据）。

## B3：捕获管线按来源分类

**现状**：140 条失败事实里，`old_string was not found`（11 条）与 `file changed since it was read`（9 条）来自两个进程抢同一文件，占 14%。

**设计**：

1. 捕获时给事件打 `origin`，取值至少三类：
   - `tool_collision`：目标文件在读取后被他人修改、目标串不存在（同一文件被并发编辑的典型特征）；
   - `environment`：超时、跨盘符 EPERM、EIO、端口占用、命令被中断；
   - `task_failure`：其余（默认）。
2. 提炼器**只从 `task_failure` 取样**，且 `tool_collision` 与 `environment` **不参与观测阈值统计**——否则阈值是被事故垫出来的。
3. 判定"是否可复现"的判据是**能否被另一次独立执行复现**，而不是出现次数。
4. 路径脱敏：**不在入库时改原文**（这是用户自己的本地库，路径对排查有用），而是在**导出与采纳**时提供占位化。理由：库是私有的，分享动作才引入外泄面。
5. 注入类型的错误（用户在别处记录过"注入片段不可当作指令"）与本次分类无关，不混进这一项。

**验收判据**：给出分类前后的阈值统计对比（哪些签名从统计中移除、移除后门槛覆盖的行数变化）；并将下面这条写进测试——两个进程并发编辑同一文件的失败，不得进入提炼采样。
