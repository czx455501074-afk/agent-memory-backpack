# B2 存量回填：真实库 dry-run 结果（决策依据）

这是在**你的真实库**上跑 `reclassify` 的**预演**结果，用于决定是否执行写入。预演本身不写任何一行。命令：

```powershell
<部署目录>\core\runtime\cli.js reclassify --data-dir <数据目录> --limit 500
# 确认分布后加 --yes 才会写；不带 --yes 恒为只读预演
```

## 一、结果

| 项 | 值 |
|---|---|
| 扫描的待审候选 | **408** |
| 判定会变化 | **407** |
| 已是当前判定器版本 | 1（最近一次提交时由新核心写入的） |

当前存储分布与预演后的分布：

| 类别 | 现在 | 预演后（据此推算） |
|---|---|---|
| `norm`（规范） | **256** | **约 16** |
| `memory`（记忆） | 142 | 约 370 |
| `other`（preference/material/skill） | 10 | 约 22 |

## 二、变化的形状（这才是要看的）

明细里压倒性的一类是 `[norm → memory]`，理由写着"可自动升格"。也就是说：**旧判定器把大量普通经验判成了"规范"**。规范在这个系统里不是标签——它参与准备路径的门禁判定、并且不允许被自动改写。把经验当规范存下来，会让"这条内容有多强"这件事失真。

第二类是少数 `[norm → norm]`，但 `autoPromotable` 变成 `false`，理由分两种，都值得你亲眼看：
- `provenance=agent：插件自身的推断不足以升格为参与门禁判定的硬规范，需人工显式确认`
- `作用域为 global：把单个项目的知识推广到所有项目需要人工确认`

这两条正是 B1 那道门禁存在的意义：**它们不会因为你点了"批准"就静默生效**，会先要求你显式确认。

## 三、"它确实没写"是怎么证明的

预演程序自己声明"只读取与计算，未写入任何一行"，但这只是它的话。独立证据有两条：

1. 预演后 `kind` 分布仍是 `norm 256 / memory 142`，与预演前逐项一致；
2. `classifierVersion` 计数仍为 **1**，而那 1 条正是过去几十分钟内一次真实提交写入的——若预演写了，它会变成 408。

（顺带记一个我自己的失误：我本打算用文件哈希做这个证明，但库文件被运行中的核心占用，`Get-FileHash` 返回空，空值互相相等，于是脚本给出了"未被改动"这个**假结论**。换成上面两条行为层证据才是真的。**能工作的判据比看起来严谨的判据重要**。）

## 四、建议

**建议执行**，理由是它修的是语义而不是外观：407 条待审里 407 条的"强度"标注是错的，而其中 341 条连门禁需要的字段都没有（`autoPromotable` 缺失 → 按 B1，缺失同样需要人工确认，而不是自动放行）。

**它不会做的事**：不改 `state`、不改 `discovery` 正文、不动任何已采纳的条目；旧判定会留在 `classificationPrevious` 里，可追溯。

**执行后**：`amb reclassify --data-dir <数据目录> --yes`。重跑一次 dry-run 应当报告"changed 0 / skipped 408"——这是幂等性的验收方式。

## 五、我没有替你执行的原因

这是**写你的权威数据**的操作。它安全、可追溯、可重跑，但"安全"不等于"我可以替你决定"。回填之后，"哪些候选是规范"这件事的答案会变，而你才是那个对知识库内容负责的人。
