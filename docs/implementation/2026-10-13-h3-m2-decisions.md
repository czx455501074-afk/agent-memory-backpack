# H3 与 M2 的决策（用户委托裁定）

- 日期：2026-10-13
- 背景：用户明确表示"你说的 H3 和 M2 问题，你帮我决策"。以下为裁定、依据与代价，均基于本会话的实测。

---

## H3：Codex MCP 不校验会话工作目录 —— 决策：**不修，保持"凭据即范围"**

### 为什么不修

1. **技术上做不到"做对"。** MCP 的 stdio 传输是**每个插件一份、由宿主在插件目录启动**的长驻进程，
   协议里（`initialize` / `tools/call`）**不携带会话的工作目录**。Adapter 的 `adapters/codex/.mcp.json`
   里 `"cwd": "."` 就是插件目录本身。所以在 MCP 里唯一能拿到的"目录"是**插件目录**，不是用户会话目录——
   加这样的检查要么永远通过、要么永远拒绝，两种都不是隔离。
2. **有反证：加回去会立刻坏掉。** 适配器侧做过对照：在 MCP 内加回 `cwd ⊆ projectRoot` 检查后，
   打包冒烟测试 `test/package-smoke.test.mjs` 必然失败（`Connection closed`），因为它会拒掉每一次合法调用。
   这正是本会话早前修掉的那类缺陷——**为防一个自己造不出来的风险，牺牲全部正常功能**。
3. **真正的边界本来就在凭据上，而且工作是有效的。** `init` 为每一端签发独立凭据
   （`dsh-client.json` / `codex-client.json` 各自带 token 与 `projectId`），核心**服务端按凭据强制项目范围**：
   跨项目的 get/read 一律 403/404，且本会话已用反例验证（`beta-secret` 跨项目读写均被拒）。
   所以"读到别的项目"这条路已经被堵死。
4. **残余风险的量级。** 剩下的是：在无关目录里开的 Codex 会话，仍能读到**本插件所属项目**的知识。
   那是**用户自己的知识、用户自己的凭据**——是范围语义上的不精确，不是数据泄漏。

### 代价与缓解

- 代价：MCP 不接受会话目录参数，所以"按目录隔离"只能在 **hook** 层做（hook 拿得到 cwd）。已如是记录。
- 缓解：`.mcp.json` 里加了一行 `description` 说明边界；README 记录该限制。
- **触发条件**：若将来宿主在 MCP 握手时开始传递工作目录（或插件改用能带 cwd 的传输），此项应重新评估。
  现在不修，是因为**当前协议下不存在正确实现**。

## M2：跨端去重失败（包装文本污染）—— 决策：**不做模糊归一化，改为记录限制**

### 现状（实测）

- 核心去重是**精确文本**匹配（EV-CE-02 已修并验证）：同文本 → `duplicate: true`。
- 适配器**没有**硬编码前缀；DSH 侧是 `requireString(args.discovery)` 原样透传。
- 真正把两端文本变得不同的，是**模型自己**在不同界面加了不同包装（"经验总结：" / "发现细节：" 之类）。
- 已做的软修：两端工具描述都改成"传原始纯净文本，不要加平台前缀或客套包装"。

### 为什么不引入归一化

考虑过三种更强做法，逐一否决：

| 做法 | 否决理由 |
|---|---|
| 归一化后再哈希（去空白、去常见前缀） | **会误合并**两条本来不同的发现。重复候选是"多一条待审"，错合并是"**用户提交的内容消失**"——后者不可恢复，更严重。 |
| 语义级去重（小模型判定） | 需要模型服务，超出 P0 范围，且引入不可解释的合并决策。 |
| 在 discovery 之外增设独立来源字段 | **无处可放**：适配器已不再包装，没有"来源文本"可迁移；凭空加字段只会增加运行时形状。 |

### 决策与代价

- **保持精确文本去重 + 工具描述引导**，把限制写进文档（已在 README/响应文档记录）。
- 代价（明说）：若某个模型仍自行加包装，跨端仍会产生**两条候选**。
- 为什么这个代价可接受：结果是一条**待人工审阅的重复候选**，审阅者一眼可判、一键合并；
  它是**自愈的**。而错误合并会静默丢掉用户真实提交的内容，**不可自愈**。
  **宁可有重复，不可错合并。**
- **触发条件**：若审阅队列里重复候选成为实际负担（有数据支撑，而非假设），再评估语义级方案；
  届时应先给出"误合并率"的度量，而不是直接上线模糊匹配。

---

## 两项决策的共同原则

**不确定时，选"可恢复的麻烦"而不是"不可恢复的损失"。**

- H3：加了自造的目录检查 → 每次都拒（功能全废，且无正确实现）；不加 → 范围语义略宽（凭据边界仍在）。
- M2：模糊合并 → 可能静默丢失用户提交（不可恢复）；不合并 → 多一条待审重复（可恢复）。

两处都写明了**触发重新评估的条件**，避免"因为当初这么定过"就永远不再看。
