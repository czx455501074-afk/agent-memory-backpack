## 3. 我此前结论的更正（重要）

外部测试暴露的不只是产品缺陷，也暴露了**我自己的核验盲区**。三处如实记录：

### 3.1 F22e 我的检查因环境而通过

原检查在**真实数据目录**上比较两端解析出的路径，因此只有在"两个专属凭据都存在"的机器上才通过。
报告在**全新隔离 home**（只有遗留 `client.json`）上跑同一脚本，得到 25/26、F22e 失败——同一个检查、
两个答案，由环境决定。已改为构造合成 home 并同时覆盖两种形态。

### 3.2 H2 我只测了 `get`，从未测 `read`

我此前的核验全程使用 `/v1/knowledge/get`。而注入文本以 `id@revision` 呈现（实测注入中确实出现
`alpha-style@1`），模型照抄该形式调用的是 `/v1/knowledge/read` —— **这条路由我一次都没测过**。
`get` 与 `read` 是两条路由，我只验证了其中一条。

### 3.3 H3 的成因包含我上一轮的改动

上一轮为让打包冒烟测试通过，我移除了 `CoreClient` 与 `src/mcp.ts` 的 `cwd ⊆ projectRoot` 检查
（该检查会拒绝宿主按 `.mcp.json` 的 `"cwd": "."` 启动的每一次合法调用）。移除后 Codex 侧再无范围
校验，而我当时只证明了"服务端逐请求范围校验足够"，没有补上"Codex 侧如何知道会话目录"这一环。

## 4. 已修复项（含证据）

### W4 能力检测不识别重定位的宿主

`deploy-plugin.mjs` 认 `DSH_HOME`、`amb-install.mjs` 认 `CODEX_HOME`，而 `capabilities.ts` 只从用户
主目录推导路径。结果：用环境变量部署成功的插件**被报为未安装**。

修复：检测同时认这两个变量与 `AMB_PLUGIN_DIR`（显式目标优先）。上一轮"链接无声明即为残留"的规则
与"空目录不得报已安装"的规则均保留。
证据：`verify-w4-homes.mjs` 6/6（含两条反向守卫）；`test/capabilities.test.ts` 新增用例。

### M7 discovery 在 tmp 段下误排除——**测试问题，非产品问题**

报告称 `D:\amb-wintest\tmp` 下两个 discovery 测试失败。复核结论：**生产代码正确**
（`discover()` 传相对路径），是**三处测试**用绝对夹具路径断言，宿主 TEMP 含字面 `tmp` 段时误触发
排除规则。报告只点出两处，第三处（叶子路径断言）是我在模拟环境下跑全量才发现的。

修复：三处改为判定"夹具根之下"的路径段（**未放宽任何断言**），并新增端到端用例——扫描根位于
`tmp` 段之下仍采纳文件，而根之下的 `tmp` 目录仍被跳过。
证据：`verify-m7-discovery.mjs`；在「TEMP 含 `tmp` 段」的模拟环境下全量 **331/331 通过**，
正常环境下亦 331/331。

### H7 / F22e 凭据静默回退

缺本端凭据时静默采用遗留 `client.json`（文档注明该文件是旧版写给 **Codex** 的）。该文件携带
endpoint、token、project 与 role，因此一端可能以**他端的项目或角色**行事，而所有界面都报正常配置。

修复：保留回退（拒绝会破坏旧安装），但**回退必须可见**——告警点名缺失文件、风险与补救。
`source` 取值集合未变，两个适配器解析器保持**字节相同**。
证据：`verify-f22e.mjs` **改前 2/4（两处静默回退全 FAIL）→ 改后 4/4**；`test/config-resolution.test.ts` 6/6。

### 4.4 H1 shell 绕过启发式（独立核验）

适配器侧实现了"当规范禁止写类工具时，对 shell 命令中的明确写文件写法做启发式拦截"。
我不采信其自述，独立核验（`verify-shell-bypass.mjs`，7/7）：

| 检查 | 结果 |
|---|---|
| 明确写意图必须拦截 | 10 条全拦截（`>`、`>>`、`tee`、`touch`、`mkdir`、`dd of=`、`Set-Content`、`Out-File`、`New-Item`） |
| **只读命令绝不能被误拦** | 12 条全放行，含 `2>&1`、`> /dev/null`、进程替换、管道 |
| 作用范围 | 仅在「确有写类工具被禁」且「工具是 shell」时生效 |
| 两端判定一致 | 22 条命令两端一致；两份 `gate-cache.mjs` 字节相同 |
| 已知局限**如实存在** | `python -c`、`node -e` 间接写入**仍可绕过**——这是启发式的边界，必须在文档与规范中说明，不得声称已完整防护 |

误拦比漏检更影响可用性（一旦误拦，只要规范禁了写类工具，**每一次** shell 调用都会失败），
因此负向用例与正向同等重要。README 已写明该边界与配合建议（同时禁用 shell 工具或使用只读沙箱）。

### 4.5 测试卫生（低危，但会在别人的机器上出问题）

- `test/codex-hook.test.mjs` 只设 `USERPROFILE`：`homedir()` 在非 Windows 读 `HOME`，`runHook` 又
  会展开进程环境，于是在 Linux/macOS 上该测试读的是**操作者真实主目录**，断言的却是它自己建的夹具目录。
  已同时设置两个变量（`adapter-config.test.ts` 本就是两个都设，此处是漏网的那一个）。
- `test/adapter-core.test.ts` 的非 Windows 回收分支是 `spawn('sh', ['-c', 'lsof … | xargs -r kill'])`：
  **未 await**，且依赖 `lsof`（未必安装，`-r` 还是 GNU 扩展）。缺失时静默失败、留下 detached 核心——
  正是报告在 Linux 上看到的遗留进程。现改为逐个 await、依次尝试 `lsof`/`fuser`/`ss`，并以**端口是否
  释放**作为完成条件（工具退出 0 不等于端口已释放）；测试还会断言端口确实释放，只在真的拉起了核心时才断言，
  把"静默泄漏"变成"当场失败"。

### 4.10 M1：命名未知 workflowId 的候选不再丢失（核验 7/8）

原缺陷：模型把 `workflowId` 填成库里没有的流程，`submit` 返回 404，**候选被丢弃**（外部实测 21 次
`tool.failed`，审阅队列为空）。用户写的经验是真实的，只是归属不成立——用 404 打发是错的答案。

实测：候选**保留**、**原文完整**、标为未定位（`resolved: false`）。实现**保留用户填写的 workflowId**
而不是置空，这比我最初预期的 `null` **更好**——同时说明"它声称归属哪里"和"没找到"，审阅者可据此人工确认。
容忍范围刻意很窄：`stageId` 指向该流程不含的步骤**仍然明确失败**（那是对具体步骤的断言，不是缺失指针），
且不留候选。

未通过的一项：**没填归属时，面向用户的说明文字里出现字面量 `undefined`**（「workflow undefined 不存在或
不可见」）——既泄漏内部值，语句也不成立。已回报。

**另：outbox 的"失败记录丢失"是我判断错了。** 那条用例用未知 `workflowId` 作为"必然失败"的触发器，
而 M1 正是让该情形合法成功，触发器因此失效。我用探针独立确认：换用「已存在的流程 + 不存在的步骤」
后，`attempts`/`lastError`/退避**全部正常**——失败路径从未被破坏，是测试的构造需要同步。我最初的
"store 回归"结论是错的，已更正并记录，避免后续有人去追一个不存在的 bug。

### 4.11 本轮新发现的缺陷（不在报告清单内，均由"核验"而非"实现"暴露）

| 缺陷 | 证据 | 处置 |
|---|---|---|
| `submit()` 接受自己 schema 禁止的输入 | 空/纯空白 `discovery` 被接受并落库；缺失时抛**裸 `TypeError`** | 已回报核心侧；根因是 HTTP 路径靠 zod 兜住、outbox replay 直调 `submit` 绕过了它 |
| 卸载可能**误杀无关进程** | `amb-uninstall` 对 `core.lock` 里的 pid 直接 SIGTERM→**SIGKILL**，只验"该 pid 有进程活着"，不验那是不是我们的核心 | 已回报适配器侧并要求"归属确认失败则绝不动手、也不删数据"——陈旧锁 + pid 复用会杀掉无关进程，SIGKILL 让对方无法自救 |
| 新增测试阻断全仓编译 | 静态 import `adapters/**/*.mjs`（无声明）→ `TS7016`，`noEmitOnError` 下整套跑不起来 | 已回报（本项目既有修法：动态 `import()` + 显式类型断言）。这是本会话**第二次**同类错误 |
| 同上：编译后相对路径失效 | `ERR_MODULE_NOT_FOUND: dist/adapters/dsh/index.mjs` | 已回报：须用「仓库根 + 绝对路径」，不能依赖相对路径（源码树对、编译产物不对） |

**关于 `baseRevision: 0` 的裁决（保留严格校验）**：核心侧问是否要放宽以免拒掉 0。我实测三条依据后
判定**不放宽**——已存在的 workflow 其 revision 必然是 1（导入前库才是 0），所以 0 指向一个不可能存在的
版本；`submit` 对 0 本就是 `revision_conflict`；`proposalSchema` 也拒 0。仓库里 52 处 `baseRevision: 0`
**全部是 knowledge 草稿定义**（同对象带 `kind`/`scope`/`body`/`deniedTools`），不是提案参数。M1 的容忍
针对「名义存在但库里没有」，不针对「参数本身非法」——两者必须区分。

**一处方法教训**：我曾两次用文本邻近搜索去判断"是否存在向 submit 传 0 的调用点"，两次都误报（同一条测试里
往往既有草稿定义又有提交调用，文本无法区分外层对象）。已放弃文本搜索、改用行为验证，并把结论写进探针注释。
