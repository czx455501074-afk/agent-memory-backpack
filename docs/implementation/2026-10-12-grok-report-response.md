## 3. 我此前结论的更正（重要）

外部测试暴露的不只是产品缺陷，也暴露了**我自己的核验盲区**。三处如实记录：

### 3.1 F22e 我的检查因环境而通过

原检查在**真实数据目录**上比较两端解析出的路径，因此只有在"两个专属凭据都存在"的机器上才通过。
报告在**全新隔离 home**（只有遗留 `client.json`）上跑同一脚本，得到 25/26、F22e 失败——同一个检查、
两个答案，由环境决定。已改为构造合成 home 并同时覆盖两种形态。

### 3.2 H2 我只测了 `get`，从未测 `read`

我此前的核验全程使用 `/v1/knowledge/get`。而注入文本以 `id@revision` 呈现（实测注入中确实出现
`alpha-style@1`），模型照抄该形式调用的是 `/v1/knowledge/read` —— **这条路由我一次都没测过**。
`get` 与 `read` 是两条路由，我只验证了其中一条。

### 3.3 H3 的成因包含我上一轮的改动

上一轮为让打包冒烟测试通过，我移除了 `CoreClient` 与 `src/mcp.ts` 的 `cwd ⊆ projectRoot` 检查
（该检查会拒绝宿主按 `.mcp.json` 的 `"cwd": "."` 启动的每一次合法调用）。移除后 Codex 侧再无范围
校验，而我当时只证明了"服务端逐请求范围校验足够"，没有补上"Codex 侧如何知道会话目录"这一环。

### 4.4 H1 shell 绕过启发式（独立核验）

适配器侧实现了"当规范禁止写类工具时，对 shell 命令中的明确写文件写法做启发式拦截"。
我不采信其自述，独立核验（`verify-shell-bypass.mjs`，7/7）：

| 检查 | 结果 |
|---|---|
| 明确写意图必须拦截 | 10 条全拦截（`>`、`>>`、`tee`、`touch`、`mkdir`、`dd of=`、`Set-Content`、`Out-File`、`New-Item`） |
| **只读命令绝不能被误拦** | 12 条全放行，含 `2>&1`、`> /dev/null`、进程替换、管道 |
| 作用范围 | 仅在「确有写类工具被禁」且「工具是 shell」时生效 |
| 两端判定一致 | 22 条命令两端一致；两份 `gate-cache.mjs` 字节相同 |
| 已知局限**如实存在** | `python -c`、`node -e` 间接写入**仍可绕过**——这是启发式的边界，必须在文档与规范中说明，不得声称已完整防护 |

误拦比漏检更影响可用性（一旦误拦，只要规范禁了写类工具，**每一次** shell 调用都会失败），
因此负向用例与正向同等重要。README 已写明该边界与配合建议（同时禁用 shell 工具或使用只读沙箱）。

### 4.5 测试卫生（低危，但会在别人的机器上出问题）

- `test/codex-hook.test.mjs` 只设 `USERPROFILE`：`homedir()` 在非 Windows 读 `HOME`，`runHook` 又
  会展开进程环境，于是在 Linux/macOS 上该测试读的是**操作者真实主目录**，断言的却是它自己建的夹具目录。
  已同时设置两个变量（`adapter-config.test.ts` 本就是两个都设，此处是漏网的那一个）。
- `test/adapter-core.test.ts` 的非 Windows 回收分支是 `spawn('sh', ['-c', 'lsof … | xargs -r kill'])`：
  **未 await**，且依赖 `lsof`（未必安装，`-r` 还是 GNU 扩展）。缺失时静默失败、留下 detached 核心——
  正是报告在 Linux 上看到的遗留进程。现改为逐个 await、依次尝试 `lsof`/`fuser`/`ss`，并以**端口是否
  释放**作为完成条件（工具退出 0 不等于端口已释放）；测试还会断言端口确实释放，只在真的拉起了核心时才断言，
  把"静默泄漏"变成"当场失败"。

### 4.10 M1：命名未知 workflowId 的候选不再丢失（核验 7/8）

原缺陷：模型把 `workflowId` 填成库里没有的流程，`submit` 返回 404，**候选被丢弃**（外部实测 21 次
`tool.failed`，审阅队列为空）。用户写的经验是真实的，只是归属不成立——用 404 打发是错的答案。

实测：候选**保留**、**原文完整**、标为未定位（`resolved: false`）。实现**保留用户填写的 workflowId**
而不是置空，这比我最初预期的 `null` **更好**——同时说明"它声称归属哪里"和"没找到"，审阅者可据此人工确认。
容忍范围刻意很窄：`stageId` 指向该流程不含的步骤**仍然明确失败**（那是对具体步骤的断言，不是缺失指针），
且不留候选。

未通过的一项：**没填归属时，面向用户的说明文字里出现字面量 `undefined`**（「workflow undefined 不存在或
不可见」）——既泄漏内部值，语句也不成立。已回报。

**另：outbox 的"失败记录丢失"是我判断错了。** 那条用例用未知 `workflowId` 作为"必然失败"的触发器，
而 M1 正是让该情形合法成功，触发器因此失效。我用探针独立确认：换用「已存在的流程 + 不存在的步骤」
后，`attempts`/`lastError`/退避**全部正常**——失败路径从未被破坏，是测试的构造需要同步。我最初的
"store 回归"结论是错的，已更正并记录，避免后续有人去追一个不存在的 bug。

### 4.11 本轮新发现的缺陷（不在报告清单内，均由"核验"而非"实现"暴露）

| 缺陷 | 证据 | 处置 |
|---|---|---|
| `submit()` 接受自己 schema 禁止的输入 | 空/纯空白 `discovery` 被接受并落库；缺失时抛**裸 `TypeError`** | 已回报核心侧；根因是 HTTP 路径靠 zod 兜住、outbox replay 直调 `submit` 绕过了它 |
| 卸载可能**误杀无关进程** | `amb-uninstall` 对 `core.lock` 里的 pid 直接 SIGTERM→**SIGKILL**，只验"该 pid 有进程活着"，不验那是不是我们的核心 | 已回报适配器侧并要求"归属确认失败则绝不动手、也不删数据"——陈旧锁 + pid 复用会杀掉无关进程，SIGKILL 让对方无法自救 |
| 新增测试阻断全仓编译 | 静态 import `adapters/**/*.mjs`（无声明）→ `TS7016`，`noEmitOnError` 下整套跑不起来 | 已回报（本项目既有修法：动态 `import()` + 显式类型断言）。这是本会话**第二次**同类错误 |
| 同上：编译后相对路径失效 | `ERR_MODULE_NOT_FOUND: dist/adapters/dsh/index.mjs` | 已回报：须用「仓库根 + 绝对路径」，不能依赖相对路径（源码树对、编译产物不对） |

**关于 `baseRevision: 0` 的裁决（保留严格校验）**：核心侧问是否要放宽以免拒掉 0。我实测三条依据后
判定**不放宽**——已存在的 workflow 其 revision 必然是 1（导入前库才是 0），所以 0 指向一个不可能存在的
版本；`submit` 对 0 本就是 `revision_conflict`；`proposalSchema` 也拒 0。仓库里 52 处 `baseRevision: 0`
**全部是 knowledge 草稿定义**（同对象带 `kind`/`scope`/`body`/`deniedTools`），不是提案参数。M1 的容忍
针对「名义存在但库里没有」，不针对「参数本身非法」——两者必须区分。

**一处方法教训**：我曾两次用文本邻近搜索去判断"是否存在向 submit 传 0 的调用点"，两次都误报（同一条测试里
往往既有草稿定义又有提交调用，文本无法区分外层对象）。已放弃文本搜索、改用行为验证，并把结论写进探针注释。

### 4.12 M6 已核验；W3 与 H6/W2 的归属验证仍有缺口

**M6 已修复并核验**：不带 `expiresAt` 导入的 material **导入后立即可读**（此前是 `not_found`）、
`cleanup` 之后**仍在库中**、读取 200。实现的取舍我认可：默认值补在**导入边界**而非 schema，保留
`expiresAt: 0 = 立即失效` 这个唯一能表达"已过期"的语义，并**如实报告**仍不可读的条目。

**W3：收紧逻辑对，但复核步骤写错了，导致 `init` 在 Windows 上恒非零退出。**

实测 `init` 对每个凭据报失败并以 exit 1 结束：

```
ACL FAILED codex: 已执行收紧，但无法复核 ACL：icacls /save 退出 87
```

根因：`icacls <file> /save <目录>` **exit 87、不写任何文件**；必须传**文件路径**才行（实测
`icacls <file> /save out.acl` → exit 0）。代码里那句"an explicit destination name cannot be supplied"
的前提是错的。另外 `/save` 写出的是 **UTF-16LE**（代码里 `TextDecoder('utf-16le')` 是对的，别改）。

**这条回归没有任何测试覆盖**——`npm test` 345/345 全绿却没有一条断言 `init` 的退出码。这本身是覆盖缺口。

**H6/W2：`verifyCoreProcess` 的归属验证不足。** 它用 `/health` 探测（先 `core.lock` 的 port，再
`core.json` 的 endpoint），拿到 `protocolVersion===1 && status==='ok'` 就放行。但**健康探测只能证明
"该端口上有核心在服务"，不能证明"锁里那个 PID 就是它"**。于是：锁中的 PID 陈旧 → 该 PID 已被复用给
无关进程 → 同时确有核心在监听该端口 → 探测通过 → **SIGTERM/SIGKILL 发给那个无关进程**。

正确的做法是把 pid 与监听者**绑定**：按端口反查 owning pid（Windows `Get-NetTCPConnection -LocalPort
<port> -State Listen` 的 `OwningProcess`），要求其中包含锁里的 pid；做不到的平台应降级为"不自动杀、
只提示人工处理"，而不是退回只靠健康探测。

**该实现已做对、应保留的部分**：验证不通过时**拒绝发信号且不清理数据**、并发/陈旧锁的分类处理、
先 SIGTERM 限时等待再升级、停不下来如实报告状态。

### 4.13 H6 / W2 / M5：卸载与部署的最终状态

**H6 / W2 已修复并核验。** 卸载现在读 `core.lock`、先停核心、等它退出、再删数据——这正是 W2 需要的：
Windows 上核心持有 `knowledge.sqlite`，先删会 EPERM 并留下半删除状态（凭据没了、库还在、进程仍在监听）。

**归属绑定（我在核验中提出的最严重问题）已解决。** `verifyCoreProcess` 现在把 pid 与 socket 绑定：
向内核询问**谁拥有该监听端口**（Windows `Get-NetTCPConnection … OwningProcess`，POSIX `lsof -Fp`），
要求其中包含锁里的 pid。健康探测只作为**前置**条件（先要求"它是我们的核心"，再要求"它是这个 pid"）。

**关键的一点**：查不到归属时**拒绝**发信号、**拒绝**清理数据，且该拒绝**对所有平台生效**——我复核时发现
原先的兜底写成 `listeningPids.length === 0 && platform === 'win32'`，于是 POSIX 上查不到归属会**落到
`verified: true`**，退化回"只靠健康探测"。已改为空列表即拒绝。

`test/uninstall-verification.test.mjs` 覆盖了关键用例：锁里写一个**存活的无关 pid**、端口上有**真实**
HTTP 服务、断言脚本拒绝发信号、**那个无关进程仍然存活**、数据目录与库完好。另外覆盖陈旧锁清理与重复
执行收敛。

**M5 是我自己上一轮引入的回归。** 复核后确认：`deploy-plugin.mjs` 在**写入清单之前**取了 `activated`，
却在**写入之后**用它判定失败，于是首次部署（把包推进 bundles、写盘成功）反而报 `active=false` 且 exit 1，
而第二次运行因为条目已在而 exit 0——**做了事的那次报失败，没事可做的那次报成功**，会教用户忽略这个
命令的退出码。已改为写完后**重新读取清单**判定（与同文件 `wired` 的做法一致），无 bundles 列表的 profile
报 `n/a` 而非失败。

**我那条守这项的检查本身也是坏的**：它 grep 源码文本，所以行为错了它照样通过、文本一改它又报失败。
已改为**行为验证**（真跑脚本、读退出码与产出清单），9/9 通过，覆盖：首次部署 exit 0 且真的写进 bundles、
二次幂等、链接位置是真实目录时拒绝并非零退出、无 bundles 列表时 exit 0 且报 `n/a`。

### 4.14 M2 与 M3

**M2 适配器侧已不再包装**：DSH 直接把模型给的文本透传（`requireString(args?.discovery, 'discovery')`），

加了包装，跨端仍会得到两条候选。这是精确匹配的固有边界，要彻底解决需要语义级判定（设计把它归入
需模型服务的一侧）。报告建议的"把来源放进独立字段"未被采用，因为**当前已无包装可放**。

**M3 未修复，且是结构性的**：outbox 存在于**核心内部**，适配器入队走 HTTP 到核心——所以核心不可达时

### 4.15 交叉核验：M6 的修复是否破坏了此前修好的 F08

M6 用「导入边界给默认有效期」修好，核心侧如实报了它的代价：`import()` 现在会把 `expiresAt <= 0`
改写成 90 天，于是写 `0` 不再表达"已过期"。这条取舍正好落在 F08 上——F08 修的是**过期必须经得起备份
往返**，若恢复备份会把过期条目的有效期改写成新的 90 天，那就是同一个缺陷换条路回来。

两者必须一起测（各自单独看都正确，只有组合起来才可疑）。结果：

| 检查 | 结果 |
|---|---|
| 未声明有效期的资料可用（M6 的修复） | **通过**：可读、在活动资料中 |
| **已过期（真实过去时间戳）恢复备份后仍不可读**（F08 的修复） | **通过**：恢复前后均 `not_found`、不进入活动资料 |
| `expiresAt: 0` 现在表示"未声明"并按默认给 90 天 | **通过**（有意变更，断言其语义并记录代价） |

**结论：F08 在真正有意义的情形下完好**——用过去时间戳表达的过期，经备份往返仍然过期。
`0` 的语义变化是**有意的**：真实输入要么省略该字段（M6 要修的正是这种），要么给一个日期来表达过期。
代价如实记录：手写的 `expiresAt: 0` 不再表示"已过期"，要表达该意图必须写过去的时间戳。
（我最初写这条探针时按**旧**语义断言，于是先报了 FAIL；查清是语义有意变更后改为断言新语义，而不是
把变更当成回归。）

12 次与 core outbox 语义对齐，超限抛错，注释写明"仅入口缓冲、送达即删、不得成为第二套权威队列"。
**但全仓库没有任何代码引用它**（`index.mjs`、`hook.mjs`、`test/` 均 0 处），只是被加进了
`package.json` 的 files 列表：


失败路径照旧丢事件，因此这是**死代码**：现象一点没变。我明确拒绝提交它——提交死代码会让人以为 M3 已修。

**我在接线前先审了三处会让"接了也丢"的问题**（已回报）：
1. `saveSpool` 用 `writeFileSync` 直写目标文件，**非原子**。写一半被 kill（或磁盘满）得到半个 JSON，
   而 `loadSpool` 的 `catch { return [] }` 会把损坏文件读成**空**——**全部暂存事件一次性消失且无信号**。
   这是持久化机制，意义就是扛住失败，必须改成写临时文件 + `renameSync`。
2. 损坏文件会被**静默覆盖**：`loadSpool` 读坏返回 `[]` → 调用方 push → `saveSpool` 覆盖该文件，原本
   可能恢复的条目被销毁且不留记录。应把坏文件改名留证（如 `adapter-spool.corrupt-<ts>.json`）。
3. 模块注释承诺 "spool errors never throw to the host agent"，但 `spoolEnqueue` 容量超限时**会 throw**。
   注释、实现、调用方三者必须一致；否则该异常会顺 host 调用链抛出去，变成我警告过的"新的单点故障"。

**三处已全部修好，模块独立核验 12/12 通过**（探针 `.local/verify-r0/security/verify-m3-spool.mjs`，
真跑模块、真写临时文件）：入队可读回、同 key 合并、**超条目上限明确拒绝**（第 500 条返回
`{enqueued:false, reason:'capacity_exceeded'}`，既有 500 条完好）、**超字节上限明确拒绝**（约 1MiB/条时
第 3 条被拒，说明字节上限不靠条目数兜底）、TTL 与尝试上限正确剪枝、损坏文件不崩且**留证为
`.corrupt-<ts>`**（不被静默覆盖）、写入结果为完整可解析 JSON、**无临时文件残留**、清空后不留空壳。

**一处我自己的探针错误如实记录**：我最初按"容量超限应**抛异常**"断言，于是报了 FAIL——实际实现改成了
**返回 `{enqueued:false, reason}`**（正是我上一条倾向的写法）。真正的要求是"**调用方能明确区分于成功**"，
抛异常与返回失败都满足，我的断言却绑定了机制。改为断言要求后通过。这段已写进探针注释，避免以后有人
照着旧契约去"修"一个正确的实现。

**M3 仍记为未修复**：模块已达标，但**接线与测试仍未完成**——`index.mjs`、`hook.mjs`、`test/` 对它
均 0 处引用，失败路径照旧丢事件。
