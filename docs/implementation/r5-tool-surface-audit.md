# MCP 工具面审计：一个对 agent 可见、却必然失败的写工具（R5）

审计 agent 实际能触达的那一面（MCP 工具），逐个工具对照服务端权限边界。本文件只做审计，**未改动任何代码**。

## 一、发现：`amb_structure_skill` 对 agent 不可用，但它被注册了

三处事实拼在一起就构成矛盾：

| 层 | 事实 | 位置 |
|---|---|---|
| MCP 工具面 | 注册了 `amb_structure_skill`，描述为"Convert an adopted skill into a real workflow"，**参数里有 `derivedBy`，默认值就是 `'agent'`** | `src/mcp.ts` |
| 服务端边界 | `/v1/knowledge/structure` **在 `ADMIN_ONLY` 集合里** | `src/server.ts:65` |
| MCP 用什么凭据 | `createMcp(client: CoreClient, ...)`，`client.adapter` 即适配器身份（`'codex'`），**不是 admin** | `src/mcp.ts:18`、`src/mcp.ts:75` |

而服务端对 admin-only 端点的判定是**在 handler 之前**的（`src/server.ts:227-228`：`if (ADMIN_ONLY.has(url) && role !== 'admin') throw 403`）。这条顺序此前已被实证：用适配器凭据调 `/v1/proposals/list` 会得到 `forbidden` + `ADMIN_ONLY_HINT`。

**于是**：agent 调用 `amb_structure_skill` 会稳定地得到 403。工具在它的工具列表里**看起来可用**，描述里也**没有任何提示**说它需要更高权限。

## 二、为什么这不是小事

1. **agent 会去试**。工具存在、描述正常、参数齐全，`derivedBy` 的默认值还专门写着 `'agent'`——这是一份明确的邀请。
2. **每次失败都会变成待审候选**。失败事实由捕获管线记录，于是"我尝试把技能结构化但被拒绝"会进入审核队列。这不是假设：本次会话的普查里就有一批来自工具失败的条目。**权限配置错误会污染这个插件自己要人审的队列。**
3. **能力事实上不存在**。库里 `workflow` 条目为 **0**，而"把已采纳技能转成流程"是唯一能产生它们的路径。也就是说：**设计里有一条建立流程库的路径，但没有任何调用方能走通它**（人能走，但要人主动去用桌面控制台，而不是由 agent 在干活时顺手完成）。
4. 这与归属机制直接相关：候选的 `attribution` 全部"已记录但解析失败"（377/377），因为它们指向不存在的流程。**把这个工具接通，是解开归属死结的第二条路**——W11 说"第二阶段方向不必做"，是因为它只看到"第一阶段已证明候选不因未归属而卡住"；但从"库里没有一条流程"这个角度看，这条路仍然值得接通。

## 三、三个选项（都需要产品判断，不是纯技术选择）

**选项 A：从 MCP 工具面移除它。** 承认"结构化"是人的动作，由桌面控制台或 CLI 完成。改动最小、最安全；代价是 agent 在干活时顺手把技能结构化这条路彻底没有。

**选项 B：把 `/v1/knowledge/structure` 移出 `ADMIN_ONLY`，但补约束。** 让它成为适配器可调用，但必须保证它**不能让 agent 写入未经人审核的内容**。风险很实：`workflow` 的正文由调用方（agent）提供，若不加约束，这就成了"绕过候选队列直接写有效知识库"的通道——正是 `ADMIN_ONLY` 注释里为 export/import 写下的那条理由。若走这条，至少需要：只允许对**已采纳**的 skill 操作、`derivedBy` 如实记录、evidence 必填（已有）、且**结构化产物应可回溯到原文**（现在有 `source` 字段，需要确认它是否被强制）。

**选项 C：保留 admin-only，但把事实写进工具描述。** 最保守：告诉 agent"这需要用户授权，适配器凭据会得到 403，请让用户执行"。避免白试与队列污染，但不解决"能力不存在"。

**我的倾向**：先做 C（一行描述的改动就能消除 1 与 2 两项危害），把 B 留给下一阶段并附带上面那组约束。A 只有在确定"永远不需要 agent 参与结构化"时才选。

## 四、这次审计没有做的事

- **没有实际调用该端点验证 403**（会写库的风险虽然低——权限检查在 handler 前——但没有必要冒）。结论由"代码所在集合 + 既有同类实证"得出，属于**代码级确定 + 同类行为实证**，不是该端点的一次实测。
- ~~没有逐个核对全部 15 个工具的权限一致性~~ **已完成**：新增 `scripts/verify-tool-surface.mjs` 做机械对账（解析工具注册与其调用的端点，与 `ADMIN_ONLY` 求交）。结果：**14 个工具中恰好只有上面那两个不匹配，没有第三个**；其余 12 个（`amb_prepare`、`amb_search_*`、`amb_read_*`、`amb_checkpoint_task`、`amb_task_activity`、`amb_save_material`、`amb_submit_experience`、`amb_inspect_archive` 等）调用的端点都在适配器权限内。脚本对那两项标注"已知并已处置"，只在**出现新的不匹配**时才以非零退出——一个永远红的检查等于没人看。
- **仍未做的**：反方向的问题——"适配器**能**调到、但语义上不该由它调"。这需要逐个工具读语义，脚本给不出结论；本次没有做。

- **`amb_supersede_experience` 已确认有同样的矛盾**（`/v1/knowledge/supersede` 与 structure 写在同一行，`src/server.ts:65`），不是猜测——两条都按下面第五节处理了。

## 五、已做的最小修复（选项 C）

`src/mcp.ts` 里两个工具的描述已改为说明 admin-only、指名 403、并提示让用户执行而不是重试（提交 `a62cc63`）。**服务端权限未改动**——"适配器能否结构化技能"是产品判断，不是这一轮该顺带决定的事。

这次改动也顺带记下一条操作教训：我在两条实现线**正在编辑源码**时跑了一次 `npm run build`，把它们**在途的半成品**编译进了 `dist`，随后跑出的 7 条失败反映的是中间状态，不是回归。**在有在途线时构建，会让"当前测试结果"这句话失去意义。** 正确顺序是先确认没有人在改，再构建、再测。
